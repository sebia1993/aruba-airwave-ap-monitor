# AirWave HTTPS·프록시 연결 장애 진단

이 안내는 사내 Windows 11에서 수집 시작 시 `TLS 보안 연결 실패 / HTTP_STATUS=미수신`이 나타나는 경우에 사용한다.
실환경 AirWave·프록시·인증서는 개발 환경에서 검증하지 않았다.

## 연결 진단 순서

1. `연결 설정`에서 **실제 프로세스 실행 계정**, AirWave HTTPS 출처(FQDN 또는 IP), 연결 경로(System/Direct/Fixed)를 확인한다.
2. 연결 방식이 **System**이면 Windows 실행 계정의 프록시/PAC 정책이 적용되는지 담당자와 확인한다. **프록시 경로 추정**은 .NET 기본 프록시 선택 결과일 뿐 실제 통신 경유나 인증 성공의 증명이 아니다. 웹브라우저 계정과 수집기 실행 계정이 다르면 결과도 다를 수 있다.
3. **연결 진단 실행** 후 실패 단계, 서버 이름과 인증서 신뢰 체인의 판정, HTTP_STATUS, 로그인/AP 요청 수를 차례로 확인한다. 두 판정을 따로 보여주는 기능은 `0.1.3-preview.1`부터 제공한다.
4. HTTP_STATUS가 **미수신**이면 HTTP 인증/403·AP 목록 파싱·유효 AP 0대가 주된 오류가 아니다. 프록시 또는 인증서/보안 연결을 먼저 해결한다.
5. TLS가 정상이고 HTTP 상태가 수신되면 **로그인 → AP 목록 읽기 → XML 파싱 → 감시 범위** 순서로 확인한다. 정식 수집과 진단은 별도 작업이다.

## 서버 이름과 인증서 신뢰 체인 읽기

| 연결 진단 결과 | 수집 PC에서 확인할 사항 |
|---|---|
| 서버 이름 불일치, 체인 정상 | AirWave의 공식 접속 주소와 서버 인증서의 SAN(주체 대체 이름)을 대조한다. IP로 접속한다면 해당 IP가 인증서에 등록되어 있는지 확인한다. |
| 서버 이름 일치, 체인 실패 | 체인 세부 사유를 확인한다. 신뢰되지 않은 루트이면 수집 계정에 배포된 사내 루트 CA를, 불완전한 체인이면 서버 또는 검사 프록시가 제공하는 중간 인증서를 담당자와 확인한다. 유효기간 오류이면 인증서의 유효기간과 PC 시각을 확인한다. |
| 서버 이름 불일치, 체인 실패 | 접속 주소와 인증서 이름, 발급 체인을 각각 확인한다. 한쪽을 조치한 뒤 같은 실행 계정과 프록시 설정으로 다시 진단해 두 판정을 비교한다. |
| 원인 미확인 | 인증서 미제공 또는 Windows가 세부 판정을 반환하기 전 연결이 종료됐을 수 있다. TLS 결과, 실패 단계, HTTP_STATUS, 프록시 경로 추정을 함께 확인한다. |

HTTPS 프록시 자체의 인증서에서 실패하면 화면에 **프록시 인증서**라고 표시한다. 이 경우 먼저 프록시 주소와 프록시의 인증 경로를 확인한다. 이 단계에서는 AirWave 서버의 인증서가 아직 관측되지 않았다.

기존 IP 대신 담당자가 확인한 호스트명으로 시험하려면 새 Live 데이터 폴더를 선택하고 읽기 계정을 등록한다. 같은 데이터 폴더는 최초 등록한 서버 주소에 연결되어 있다. 실행 방법은 [Windows 실행 옵션](WINDOWS_RUN.md)을 참고한다.

## IP·포트로 접속할 때 인증서 지문 자동 조회

`0.1.3-preview.4` 이상에서 **연결 설정 → AirWave 인증서 지문**으로 이동한다. 저장된 IP·포트를 확인하고 **인증서 자동 조회**를 누른다. 수집기는 현재 프록시 설정을 사용해 서버의 인증서를 조회한다. 조회 중에는 AirWave 로그인 정보가 전송되지 않는다.

| 조회 결과 | 다음 조작 |
|---|---|
| 기존 등록 지문과 일치 | **해제할 때까지 허용**을 누른다. 현재 지문이 다시 확인되면 허용 상태가 **사용 중 · 해제할 때까지**, 만료 시각이 **자동 만료 없음**으로 표시된다. |
| 등록된 지문 없음 또는 기존 허용 기간 만료 | 서버의 관리 기록이나 설치 때 보관한 원본 인증서에서 SHA-256 지문을 확인한다. **관리 기록에서 별도로 확인한 SHA-256 지문** 칸에 입력한다. 조회한 값과 일치하면 **해제할 때까지 허용**을 누를 수 있다. |
| 서버 인증서 변경 감지 | 서버 또는 TLS 종단의 인증서 교체 여부를 관리 경로에서 확인한다. 교체를 확인했다면 **지문 허용 해제 → 인증서 자동 조회**를 누르고 새 인증서 지문을 독립적으로 확인해 등록한다. |

SHA-256 지문을 계산하려면 신뢰하는 관리 경로에서 받은 공개 서버 인증서 한 장을 **DER 인코딩 바이너리 X.509 (.cer)** 로 저장하고 Windows PowerShell에서 다음 명령을 실행한다. 경로는 실제 파일 위치로 바꾼다.

```powershell
(Get-FileHash -LiteralPath 'C:\Temp\airwave-server.cer' -Algorithm SHA256).Hash
```

등록 후 **연결 진단 실행**에서 TLS의 **등록 지문으로 연결** 표시와 진단 제목 **읽기 성공**을 확인한다. 정상적인 Windows 인증서 검증도 통과한 경우 TLS에는 **HTTPS 연결 검증 통과**가 표시될 수 있다. 운영 수집은 **AP 현황 → 수집 도구 → 지금 수집**을 누른 다음 **관리 → 수집 기록 → 기록 새로고침**에서 새 회차로 확인한다.

이전 버전으로 되돌릴 계획이 있다면 무기한 전환 전에 데이터 폴더를 백업한다. `0.1.3-preview.3` 이하에서는 무기한 지문을 저장한 설정과 수집 회차를 읽을 수 없으므로, 되돌릴 때에는 전환 전 백업을 사용한다.

기존 시간제 등록은 업데이트해도 저장된 만료 시각까지 적용된다. **기간을 지정해 지문 직접 등록**을 열면 기본 24시간, 1~168시간으로 저장할 수 있다. **해제할 때까지 허용**은 지정한 IP·포트의 등록 인증서 한 장에 적용되며 수집기를 재시작해도 유지된다. 다른 인증서가 관측되면 로그인 전 수집을 차단한다. 정상적으로 신뢰되는 인증서로 서버를 교체한 뒤에는 **지문 허용 해제**를 누르고 연결 진단을 다시 실행한다.

`0.1.3-preview.2`에서 진단은 HTTP 200인데 실제 수집 회차가 임시 고정 조건 오류로 실패했다면 `0.1.3-preview.3`부터 수정된 항목이다. 기존 Live 데이터 폴더와 같은 실행 계정으로 업데이트하고 새 수집 회차를 확인한다.

## TLS 실패 원인별 판단

| 코드 | 안내 | 현장 확인 |
|---|---|---|
| pin-mismatch | 등록 지문과 서버 지문 불일치 | 서버 인증서 교체 여부와 실제 종단의 IP·포트를 관리 경로에서 확인 |
| pin-expired | 임시 허용 기간 만료 | 저장된 만료 시각 확인. 관리 경로에서 지문을 다시 확인하고 원하는 허용 기간으로 등록 |
| pin-disallowed | 예외 적용 조건에 맞지 않음 | 프록시 자체의 인증서, 불완전한 체인, 중간 CA 만료, 폐기 상태 등의 오류를 확인. 지문 예외가 허용하는 항목은 서버 이름 불일치, 신뢰되지 않은 루트, 서버 인증서 자체의 만료 |
| certificate-name-mismatch | 인증서 서버 이름 불일치 | 입력한 AirWave 주소와 인증서 SAN/호스트 이름을 일치시키는지 확인 |
| certificate-expired | 인증서 만료 | 서버 인증서 갱신과 수집 PC 시각 확인 |
| certificate-not-yet-valid | 인증서 유효기간 시작 전 | 수집 PC 시각·인증서 시작 날짜 확인 |
| certificate-trust-chain | 신뢰 체인 오류 | 승인된 사내 루트/중간 CA, SSL 검사 프록시의 발행자 확인 |
| certificate-missing | 인증서를 받지 못함 | 서버·프록시 TLS 종단 확인 |
| certificate-validation-failed | 그 외 인증서 검증 오류 | Windows 인증서 정책·체인 상태 확인 |
| tls-handshake-or-certificate | 협상 또는 인증서 검증 실패(원인 미확정) | TLS 버전·암호군·PAC 및 프록시·인증서 모두 확인 |

일부 Windows TLS 실패는 세부 인증서 검증 이벤트 없이 종료된다. 이 경우 원인을 임의로 신뢰 체인·이름 불일치라고 확정하지 않는다.

## AP 0대 표시 정책

- **TLS/전송/인증 오류로 전체 수집이 실패**하면 `유효한 AP 상태가 0대`라는 추가 경고를 만들지 않는다.
- **HTTP 응답을 수신한 뒤 AP 목록이 빈 상태이거나 상태 자료가 유효하지 않다면** AP 0대/대상 점검 안내를 유지한다.
- 전체 실패 중 기존 미복구 사건은 닫지 않으며 마지막 정상 상태를 보존하고 이번 회차를 확인 불가로 기록한다.
- 실제 운영 AP 전체가 Down인지 여부는 프로그램의 통신 실패로 판단하지 않는다.

## 보안 및 운영 제한

- **인증서 검증 비활성화(accept-all), 프록시 우회, Windows 전역 CA 변경을 자동으로 하지 않는다.**
- 사내 인증서를 승인된 경로로 배포하거나 관리자의 정책 승인을 받은 후에만 설정을 수정한다.
- 비밀번호, X-BISCOTTI, 세션 쿠키, 원문 AP 응답, 인증서 원본, 내부 프록시 주소를 GitHub 이슈나 공개 로그에 업로드하지 않는다.
- 배포 버전과 데이터 디렉터리는 분리하고, 변경 전에 백업한다.
- 실환경 결과는 `ONSITE_VALIDATION.md`에 **미확인/실패/통과**로 구분해 기록한다.

관련 코드: `AirWaveSession.cs`, `TlsCertificateDiagnostics.cs`, `AirWaveClient.cs`, `ConnectionDiagnostics.cs`, `SqliteCollectionStore.Apply.cs`.
