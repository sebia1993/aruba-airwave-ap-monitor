# Windows 초기 연결 진단 패키지

Task 2용 `0.1.0-diagnostics` 패키지다. AirWave 연결 설정·계정 등록과 **한 번의 AP 목록 조회를 포함한 연결 진단**을 제공한다. 자동 감시, SQLite 저장, 장애·복구 이력, 서비스·예약 작업 설치는 후속 작업이다. 진단 ID는 운영 회차 ID가 아니며 조회 결과를 장애 기록으로 저장하지 않는다.

## 실행

1. ZIP과 같은 이름의 `.zip.sha256`에 적힌 값을 `Get-FileHash -Algorithm SHA256 .\패키지.zip` 결과와 비교한다. ZIP 전체를 쓰기 가능한 새 폴더에 푼다. `app` 안의 파일을 따로 이동하지 않는다. 별도 .NET 설치나 인터넷 CDN은 필요하지 않다.
2. Windows PowerShell에서 압축을 푼 폴더로 이동한다. `powershell.exe -File .\Start-Monitor.ps1 -Mode live -DataDirectory 'C:\운영 자료\AirWaveLive'`로 실행한다. 데이터 폴더는 실행 계정이 쓸 수 있는 새 전용 폴더를 지정한다. 사내 실행 정책이 스크립트를 차단하면 정책을 임의 변경하지 않고 `& '.\app\AirWaveApMonitor.App.exe' --mode live --data-dir 'C:\운영 자료\AirWaveLive' --port 8765`로 직접 실행하거나 담당자에게 확인한다.
3. 같은 PC 브라우저에서 `http://127.0.0.1:8765`를 연다. 창을 닫거나 Ctrl+C를 누르면 앱도 종료된다. 다른 PC에 공개하는 서버가 아니다. 포트 충돌 시 실행 인수 `-Port`(직접 실행 시 `--port`)와 브라우저 주소를 함께 바꾼다.
4. 화면의 **실제 프로세스 실행 계정**을 확인하고 HTTPS AirWave 출처를 저장한다. 기본 경로는 해당 실행 계정의 OS 프록시 설정이다. 직접 연결이나 고정 프록시는 사내 담당자가 지정한 경우만 선택한다. PAC 스크립트 URL은 고정 프록시 주소로 입력할 수 없다.
5. 같은 화면에서 읽기 권한 계정을 등록하고 연결 진단을 실행한다. Windows DPAPI `CurrentUser`로 실행 계정에 묶어 보호한다. 비밀번호·쿠키·토큰·원문 응답은 진단 보고서에 포함하지 않는다. 잘못된 비밀번호로 인증이 거절되면 반복 로그인을 중단한다. 정보를 바로잡은 후 계정을 다시 등록하거나 명시적으로 재시도한다.
6. 결과의 연결 경로·TLS·HTTP·인증·AP 조회·파싱 건수를 확인한다. TLS 단계에서 실패했다면 HTTP 상태는 `미수신`이다. 조회 성공만으로 전체 AP 대수나 실제 운영 상태가 검증된 것은 아니다. `ONSITE_INITIAL_CHECKLIST.md`에 실제 확인 결과를 기록한다.

가상 자료 확인은 별도 데이터 폴더로 `-Mode demo`를 명시한다. Demo는 가상 AP 자료를 같은 파서에 넣으며 실제 AirWave 연결 성공을 의미하지 않는다. Demo에서 실제 자격 증명을 등록하지 않는다. Live 연결 실패를 Demo 자료로 대체하지 않는다.

## 데이터와 계정

- 실행 파일과 데이터는 분리한다. 기본 Windows Live 경로는 `%ProgramData%\AirWaveAPMonitor\live`, Demo 경로는 `%LocalAppData%\AirWaveAPMonitor\demo`다. 기본 경로에 권한이 없으면 쓰기 가능한 별도 전용 폴더를 지정한다. 이 단계는 권한을 자동 변경하거나 관리자 실행을 요구하지 않는다.
- 한 데이터 폴더를 다른 모드로 재사용할 수 없다. 기존 표시자 없는 자료가 들어 있는 폴더도 자동 채택하지 않는다. 업데이트는 새 실행 폴더를 사용하고 동일한 Live 데이터 경로를 명시한다. 사용 중인 데이터 폴더와 자격 증명 파일을 삭제하거나 ZIP에 넣지 않는다.
- Windows 실행 계정이 바뀌거나 보호 파일을 복호화할 수 없으면 그 실행 계정에서 재등록해야 한다. 브라우저 사용자 이름으로 DPAPI 계정을 추정하지 않는다. 다른 PC로 복사한 자격 증명의 사용 가능성을 보장하지 않는다.
- macOS의 Demo 개발과 Windows CI의 현재 계정 검사는 사내 계정·Windows 11·서비스 실행·장비 상태 확인을 대신하지 않는다. 실제 Windows CI 결과는 저장소의 `docs/DEVELOPMENT_STATUS.md`에서 해당 소스 커밋과 함께 확인한다.

## 실패 확인

HTTPS 출처, 사내 DNS·방화벽·프록시, 실행 계정의 프록시 인증, 인증서 호스트 이름·기간·신뢰 체인을 담당자와 확인한다. 앱은 인증서 검증을 끄거나 신뢰 저장소·OS 프록시를 수정하지 않는다. 403은 권한·토큰 문제로 분리하며 반복 재로그인하지 않는다. 알려지지 않은 XML·HTML이나 AP 분류는 확인되지 않은 자료로 남긴다.

공식 문서 기반 로그인/목록 계약과 합성 fixture를 사용했다. 실제 버전의 응답, 비밀번호 변환 요구, 쿠키 만료 의미와 AP 범위는 사내에서 확인해야 한다. 원문 XML, 비밀번호, 인증서, DB를 외부로 보내지 않고 사내에서 대수·분류·안전한 오류 코드만 기록할 수 있다.

`VERSION.json`의 `source_commit`은 소스 식별자이며 `working_tree_dirty: true`는 커밋되지 않은 변경을 포함한 개발 빌드다. `SHA256SUMS.txt`는 자기 자신을 제외한 패키지 파일의 해시, `.zip.sha256`는 ZIP 전체 해시다. 해시는 무결성 확인용이며 전자서명이나 사내 검증 완료 표시가 아니다.
