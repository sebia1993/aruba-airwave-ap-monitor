# 화면과 자료의 의미

현재 화면, 과거 회차, 사건 스냅샷은 서로 다른 시점의 자료다. 설치본의 제공 범위와 실제 검증 결과는 [개발 기록](../DEVELOPMENT_STATUS.md), 조작 절차는 [운영 기록·대장](OPERATIONS.md)과 [연결·전력](ENRICHMENT.md)을 함께 본다.

## AP 상태와 사건

| 표시 | 뜻 | 해석할 때 주의할 점 |
|---|---|---|
| 이번 Up / Down | 선택 회차에서 유효하게 확인한 AP 상태 | 과거 마지막 상태를 이번 확인으로 대신하지 않는다. |
| 이번 미확인 | 누락·실패·중복 식별·불명 상태 등으로 이번 상태를 확인하지 못함 | Up도 Down도 아니다. 마지막 유효 상태를 별도로 볼 수 있다. |
| 마지막 유효 관측 | 마지막으로 상태가 유효했던 값·시각·회차 | 이후 실패가 있어도 이 값 자체가 새 관측으로 갱신되지 않는다. |
| 신규 Down | 직전 유효 Up에서 Down으로 전환을 관측함 | 실제 장애가 시작된 정확한 시각을 뜻하지 않는다. |
| 최초 확인 Down | 감시 기준이 없는 상태에서 처음 Down을 확인함 | 관측 시작 전부터 Down이었을 수 있다. 같은 상태가 계속돼도 매번 최초로 세지 않는다. |
| 기존 Down | 이미 진행 중이던 Down을 다시 확인함 | 새 장애 사건을 반복 생성하지 않는다. |
| 복구 확인 | Down 이후 유효한 Up을 관측함 | 누락 해소, 작업 완료, 수동 메모만으로 복구되지 않는다. |
| 미복구 / 열린 사건 | 감지 후 Up 복구가 아직 확인되지 않은 사건 | 이번 미확인 AP도 포함할 수 있어 이번 Down 대수와 다를 수 있다. |
| 추적 종료 | 감시 종료·철거·장비 교체 등으로 해당 추적을 끝냄 | 복구와 다른 종료다. 이전 사건과 근거는 남는다. |
| 관측 공백 | 해당 기간에 필요한 관측을 확보하지 못함 | 그동안 상태가 계속 같았다는 뜻도, 물리적으로 단절됐다는 뜻도 아니다. |

신규·최초·기존 Down은 이번 Down의 분류다. 이를 이번 Down에 다시 더하지 않는다. 사건 건수와 사건이 있는 AP 대수도 다를 수 있다. 전체 실패에서는 현재 Up/Down을 0대로 정상 표시하지 않으며, 알고 있는 대상의 상태를 미확인으로 두고 기존 열린 사건을 유지한다.

장애 이력의 기간은 **최초 Down 감지 시각**, 수집 기록의 기간은 **수집 시작 시각**으로 조회한다. 기간 안의 Up→Down 횟수는 최초 확인 Down을 제외한 전환 수다. 같은 AP의 세 번 전환은 사건 3건·고유 AP 1대이며 현재 Down 대수에 합산하지 않는다. 집계는 페이지에 보이는 행만이 아니라 해당 조건의 전체 사건을 기준으로 한다.

1시간·24시간 이상 미복구 필터는 선택 회차의 확정 시각에서 첫 Down 감지 시각까지의 관측 경과로 판단한다. 열린 사건만 대상으로 하고 시간 확인 필요·음수/미상 경과는 조건 충족으로 세지 않는다. 공백이 포함될 수 있으므로 실제 연속 서비스 중단시간을 뜻하지 않는다.

## 대상과 버전

| 항목 | 사용하는 이유 |
|---|---|
| 데이터셋 | 서로 다른 데이터 폴더·모드의 자료를 섞지 않기 위한 구분이다. Demo 자료를 Live로 승격하지 않는다. |
| AP 원천 ID | AirWave가 제공한 식별자다. 이름이나 IP와 다르며 서버/데이터셋 맥락과 함께 사용한다. |
| 내부 AP ID | 앱에서 AP를 정확히 선택할 때 쓰는 ID다. CSV·작업 대상에서 이름/IP를 대신 추정하지 않는다. |
| 장비 세대 | 같은 원천 AP ID 아래에서도 확인된 하드웨어 교체 전후를 구분한다. 과거 세대의 사건·수동 등록·배치를 새 세대로 옮겨 붙이지 않는다. |
| 감시 구간 | 명시적 감시 종료와 재편입을 구분한다. 종료한 구간의 사건을 새 감시의 현재 사건으로 만들지 않는다. |
| 설정 버전 / 범위 버전 | 어떤 설정과 대상 범위로 수집·편집했는지 나타낸다. 이전 범위 응답으로 새 범위의 누락을 판정하지 않는다. |
| 감시 범위 정의 | 발견한 전체 AP 또는 명시한 원천 AP ID 목록이다. 수집에서 발견한 기대 대상 목록·화면 검색 조건과 별도로 저장한다. |
| 기대 대상 목록 | 시작 당시 관측을 기대한 대상이다. 응답에서 빠진 AP를 미확인으로 판단할 때 사용하며 감시 범위 정의를 대신하지 않는다. |
| 기준 대조 기록 | 사용자가 특정 회차의 대상 목록·대수를 실제 관리 대상과 대조했다는 기록이다. API 권한이나 물리 재고의 자동 검증 결과가 아니다. |
| 등록·작업·지점·배치 버전 | 현재 편집과 당시 기록을 구분한다. 다른 창의 변경이나 복원 후에는 예전 편집을 덮어쓰지 않고 다시 확인한다. |
| 수집 회차 | 한 수집 단위의 시작·결과와 당시 자료를 묶는 번호다. AP 상태, 연결·이웃, 전력의 결과를 구분해서 읽는다. |

번호가 같아 보이는 자료라도 다른 데이터셋의 기록은 같은 대상이 아니다. 파일의 ID를 직접 수정해 자료를 합치지 않는다. 동시 편집 충돌이나 복원 뒤 미리보기 무효 메시지는 현재 값을 다시 읽고 재검토하라는 뜻이다.

감시 범위 정의·변경 사유·기준 대조 회차는 설정에 함께 보존하며 수집 시작 때 고정한다. 현재 기준 상태는 해당 설정의 확정 회차를 기준으로 읽는다. 대조 기록을 저장해도 과거 회차의 잠정 상태는 바뀌지 않으며, 새 설정으로 아직 수집하지 않았다면 관측 대기다. 대조한 대상 목록과 달라지면 다시 잠정 기준으로 다룬다.

## 시각

| 시각 | 의미 |
|---|---|
| 수집 시작 / 시도 | 앱이 해당 수집 단위를 시작한 때다. 성공 시각이 아니다. |
| 조회·수집 시각 | 앱이 자료를 읽은 때다. 장비가 그 값을 새로 측정한 때와 다를 수 있다. |
| 원천 시각 | 원천이 제공한 관측·갱신 시각이다. 의미가 확인되지 않으면 최신성도 미확인이다. |
| 검증된 측정 시각 | 전력 표본 등이 실제로 측정됐다고 해석할 수 있는 원천 시각이다. 단순 조회 시각으로 채우지 않는다. |
| 확정 시각 | 결과를 로컬 기록으로 확정한 때다. 실패 회차에도 확정 결과가 있을 수 있다. |
| 마지막 유효 확정 | 사용 가능한 관측을 저장한 최근 시각이다. 완전한 전체 확인과 별개다. |
| 마지막 완전 확정 | 해당 수집 단위가 완전하게 확인된 최근 시각이다. 부분 확인이나 다른 종류의 성공으로 갱신되지 않는다. |
| 감지 / 복구 확인 | Down 또는 Up 전환을 확인한 관측 시각이다. 실제 장애 시작·복구 순간은 알 수 없다. |
| 등록·정정 시각 / 실제 작업 시각 | 앱에 기록한 때와 사용자가 입력한 작업 시점을 구분한다. 나중에 작업 시각을 입력해도 과거 관측을 다시 쓰지 않는다. |

저장 시각과 CSV 시각은 UTC이며 화면 표시·기간/작업 시각 입력은 **한국 표준시(KST, UTC+09:00)**다. 브라우저·OS 시간대와 무관하게 같은 시각을 표시한다. 원문 시각의 `Z`·오프셋은 그대로 확인할 수 있다. 시계 역행 등의 **시각 검토 필요** 표시가 있으면 회차 순서와 원천 근거를 함께 확인한다. 관측 경과를 음수로 표시하거나 실제 장애 지속 시간으로 확정하지 않는다.

## 현황 CSV의 조회 근거

첫 데이터 행의 `RecordType=QueryContext`는 조회 조건이며 AP가 아니다. `QueryConditions` JSON에 데이터셋·범위·회차·관측 시각, 상태·검색·정렬·관리 상태·계획 작업 숨김·미복구 경과 조건과 전체 결과 대수를 기록한다. 이후 `RecordType=Ap`인 행이 실제 AP 자료다. AP 0대도 조건 행은 남으며, 표시된 내보내기 대수는 AP 행만 센다. 기존 CSV 처리 도구에서는 `RecordType=Ap`를 선택해 장비 행을 처리한다.

CSV는 선택 회차에 고정된 **전체 필터 결과**를 내보낸다. 화면의 한 페이지만 내보내는 것이 아니며 자동 원본·수동 등록·출처·당시 설치 지점과 필드별 근거도 보존한다.

## 출처와 품질

자동 원천은 **AirWave**, 가상 자료는 **Demo**, 사용자가 입력한 자료는 **수동**, CSV로 등록한 자료는 **가져오기**로 구분한다. 수동 우선 표시는 어느 설명을 화면에 먼저 보여 줄지 정하는 기능이다. 자동 원본·확인 시각·장애 판정을 바꾸지 않는다.

| 구분 | 값 | 의미 |
|---|---|---|
| 필드 제공 여부 | 제공 / 미제공 | 이번 원천에서 값이 제공됐는지 구분한다. |
| 필드 제공 여부 | 미지원 / 미검증 | 해당 기능을 지원하지 않는다는 근거가 있는 경우와, 아직 확인하지 못한 경우는 다르다. |
| 값의 유효성 | 유효 / 잘못된 값 / 미확인 | 값이 있어도 형식·범위·식별 근거가 유효하지 않을 수 있다. |
| 원천 최신성 | 최신 / 지연 / 미상 | 확인된 원천 시각 의미와 허용 나이에 따른 판정이다. 최근 조회만으로 최신으로 바뀌지 않는다. |
| 응답 완전성 | 완전 / 부분 / 미상 | 필요한 조회 범위가 모두 확인됐는지 나타낸다. 부분·미상 응답의 빈 항목은 부재 증명이 아니다. |
| 실행 결과 | 성공 / 부분 확인 / 실패 | 해당 수집 단위의 결과다. AP 성공과 부가 관측 실패는 함께 존재할 수 있다. |

한 번의 빈 값, 403, 통신 실패를 근거로 기능 전체를 미지원으로 확정하지 않는다. 제공 범위의 확인은 프로필·계정·장비 유형·필드·계약 버전에 묶인다. Demo에서 잘 보였다는 이유로 Live의 제공 확인 상태가 올라가지 않는다.

### 원천 전체와 선택 범위의 집계

선택한 감시 범위의 결과와 원천 응답 전체의 품질은 다를 수 있다. 예를 들어 선택한 AP는 유효하고 범위 밖 AP만 잘못된 값을 보냈다면, 오류의 대상이 확실한 경우 선택 범위는 성공으로 확정할 수 있다. 대상이 불명확한 공통 오류·통신 실패·설명되지 않은 부분 응답은 범위 밖 오류로 추측해 없애지 않는다.

API의 `sourceEvidence`는 다음처럼 읽는다. 선택 범위용 추가 필드가 없는 이전 자료·전체 발견 범위에서는 그 값을 0이나 성공으로 추정하지 않는다.

| 필드 | 집계 범위 |
|---|---|
| `parsedApCount` | 선택 범위로 좁히기 전, 원천에서 파싱한 전체 AP 관측 수 |
| `validStateCount` / `appliedStateCount` | 적용 범위의 유효 상태 수 / 감시 정책·실패 판정을 거쳐 실제 반영한 상태 수 |
| `excludedRecords` | 적용 범위의 제외 근거; 식별 불가 등 공통 근거도 남음 |
| `sourceOutcome` / `sourceCompleteness` | 범위 적용 전 원천 결과 / 완전성; 선택 범위에서만 추가 기록 |
| `scopeExcludedApCount` / `scopeExcludedRecordCount` | 범위 밖이라 제외한 파싱 AP 관측 수 / 제외 레코드 근거 수; 선택 범위에서만 추가 기록 |

수집 상세의 `received_records`, `excluded_records`, `error_counts_json`은 범위 적용 전 원천 집계이고 `accepted_records`는 적용한 유효 상태 수다. 따라서 원천 수신 대수와 현재 선택 범위의 대상·반영 대수가 같아야 하는 것은 아니다. 이 집계는 원문 응답 전체를 보관한다는 뜻이 아니다.

## 연결과 전력

현재 Live의 연결·전력 수집은 **미검증·비활성**이다. Demo에서 명시적으로 켜는 가상 관측과 구분하며, 실제 필드·권한 확인을 마친 기능으로 해석하지 않는다.

AP 목록의 upstream 참조, 사용자가 적은 스위치/포트, LLDP 이웃 관측은 서로 다른 정보다. 포트 Up, PoE 공급 On, LLDP 협상 지원도 LLDP 이웃을 계속 관측했다는 뜻이 아니다. 복수 연결과 관측 방향을 그대로 읽고, 기대 이웃 미관측을 케이블 제거·AP Down·장애 원인 확정으로 해석하지 않는다.

| 전력 항목 | 뜻 |
|---|---|
| AP 소비전력 | AP 자체에 귀속된 소비전력 관측 |
| 스위치 포트 실제 전력 | 특정 스위치 포트에서 관측한 실제 전력 |
| 요청 / 할당 / 예약 / 최대 전력 | 각각 요청량·할당량·예약량·최댓값이며 소비전력과 같지 않음 |
| 공급 상태 / 공급 방식 | On·Off·오류 등의 상태와 PoE 등 방식; 수치 W와 별개 |
| 오류 횟수 / LLDP 협상 지원 | 별도 카운터·지원 여부; 이웃 관측이나 장애 원인을 대신하지 않음 |

검증된 W와 mW는 W로 비교할 수 있다. dBm은 RF 송신전력, Wh/kWh는 에너지 단위이므로 PoE W로 바꾸거나 합산하지 않는다. **미제공·미확인·잘못된 값은 0 W가 아니다.** 실제 유효한 0 W 표본과 구별한다. 드문 표본으로 누적 사용량이나 전기 요금을 산출하지 않는다.

포트 표본의 AP 귀속에는 당시 연결·장비 세대·감시 구간의 근거가 필요하다. 배치가 등록돼 있으면 그 버전과 유효 시점도 검증한다. 직접 AP 소비전력도 측정 시점이 그 세대와 감시 구간의 확인된 기간 안에 있어야 한다. 근거가 모호하거나 오래됐으면 표본은 남겨도 AP 귀속은 미확인이다. 현재 연결이나 새 장비로 과거 표본을 소급 이전하지 않는다.

## 과거 조회와 보존

과거 회차·장애 감지/복구 스냅샷에는 그 기록을 만들 때 확정돼 있던 자료만 들어간다. 늦게 도착한 부가 관측, 현재 수동 대장, 새 포트·배치로 빈 칸을 채우지 않는다. 현재 목록의 새 자료를 보려면 **현재 현황으로** 또는 해당 화면의 최신 기준 다시 읽기를 사용한다.

DB schema 6부터 새 회차의 `run_rows` 상세 행은 Down·미확인 대상으로 보관한다. 정상 Up은 불변 사실 버전·대상 목록과 회차별 관측 근거를 연결해 같은 내용을 재사용한다. 공유 저장하더라도 당시 시각·품질·분류·원시 값의 차이는 보존하며, 과거 All/Up 조회나 복구 회차를 현재값으로 재구성하지 않는다. 실제 값이 달라지면 버전이 늘 수 있으므로 모든 정상 수집의 저장량이 일정하다는 뜻은 아니다.

schema 5 이하에서 올라온 기존 회차는 원래 행을 유지하고 새 표현과 함께 조회한다. 업그레이드가 기존 DB 전체를 작게 다시 쓰거나 과거 Up 행을 지우지는 않는다. 새 불변 참조도 상세 로그 정리와 별개로 보존하며, 업데이트·복원은 [백업·복원 안내](UPDATE_AND_RECOVERY.md)를 따른다.

| 자료 | 기본 보존 정책 |
|---|---|
| 장애·복구·추적 종료, 당시 스냅샷, 변경·연결·교체·이웃/전원 상태 전환, 작업·메모·수정 이력 | 자동 정리 대상 아님 |
| 과거 회차 현황과 조회에 필요한 불변 참조 | 상세 정리 후에도 유지 |
| 열린 사건·현재 상태의 필수 참조, 미종결 공백 | 상세 정리로 삭제하지 않음 |
| 종결된 수집 실행·참조가 필요 없는 종결 공백의 상세 | 90일 |
| 주기별 전력 수치 표본 | 30일; 사건에 복사한 근거와 상태 전환은 별도 유지 |
| 운영 로그 | 30일 및 파일 크기·순환 제한 |
| 일일 DB 백업 | 새 정상본 검증 후 최근 7개; 업데이트 전 별도 백업은 구분 |

일반 AP 회차가 참조하는 원시 전력 상세는 30일 정리 후 만료될 수 있으며 만료로 표시한다. 장애 감지·복구 사건에 복사한 당시 근거는 별도로 유지한다.

표본의 조회·30일 보존 기준은 앱이 읽은 조회 시각이며 원천·측정 시각은 별도 표시한다. 만료 기준이 표시된 조회에서 표본이 없다고 소비전력 0 W나 전원 중단으로 해석하지 않는다. 마지막 실제 정리 결과와 만료 표시를 확인한다. 자동 삭제 없음은 무한 디스크나 저장장치 고장 복구 보장이 아니다. [백업·복원 안내](UPDATE_AND_RECOVERY.md)를 함께 따른다.
