검증 소스는 `b5882f89e3be28c9533491b26a289525e009092f`, [전체 Windows CI는 43789827101](https://github.com/sebia1993/aruba-airwave-ap-monitor/actions/runs/43789827101)이다. [v0.1.1 릴리즈](https://github.com/sebia1993/aruba-airwave-ap-monitor/releases/tag/v0.1.1)는 이 커밋을 가리킨다. 성공한 원본 ZIP을 재포장하지 않고 파일명만 변경했다. ZIP 내부 문서는 패키지 생성 시점의 기록이며 최신 결과는 이 완료 기록과 릴리즈를 따른다. Live 부가 관측(연결·LLDP·PoE) 전송 어댑터는 미구현·미검증·비활성 상태다.

배포 파일은 `AirWaveAPMonitor-v0.1.1-win-x64.zip` 하나이며, 50,746,795 bytes / SHA-256 `44eeb6822eeae9234c2e7732ed7e2a7c3545978ea16f8ff8ad516705ebd01859`이다. 원본 CI ZIP·릴리즈용 복사본·GitHub 업로드 자산·인증 없이 공개 URL에서 다시 받은 파일의 해시와 바이트가 일치한다. 릴리즈 ID는 `446539479`, 자산 ID는 `753137738`, 게시 시각은 `2026-11-16T02:25:41Z`다.

최종 macOS 전체 검증은 공통 935, Frontend 100, Python 15 통과, Windows 전용 9개 Mac 제외, 빌드 경고·오류 0이다. Windows 전력 전용 진단 5개는 공통 검사의 일부이며 중복 합산하지 않는다. 전용 진단의 Power 적용은 3.795초·취소 없음이었다. 전체 CI에서는 6.880초 적용 성공 응답 시 토큰이 취소 상태였고, 후속 상태 조회 취소 뒤 이미 커밋된 결과를 재확인해 Finalized/Succeeded·표본 12,288개·복구 대기 없음으로 끝났다. 실제 COMMIT 전후 취소 순서는 이 로그로 확정하지 않으며 5초 이내 완료나 실환경 성능을 보장하지 않는다.

기존 v0.1.0 태그·ZIP과 원래 사용자 계획·설계·모의 화면은 보존했다. 아래는 릴리즈 완료 전 실패 및 보완 이력이다.

첫 Windows 실행 [43780557973](https://github.com/sebia1993/aruba-airwave-ap-monitor/actions/runs/43780557973)은 공통 908 통과·2 실패·4 제외였다. 두 실패는 새 실행기의 최초 HTTP 포트 확인에서 약 2초 뒤 충돌로 처리된 사례이며, 원래 예외가 기록되지 않아 정확한 OS 원인은 미확정이다. 네이티브 컴파일·Windows 전용·Python·ZIP 검사는 그 실행에서 진행되지 않았다. Windows의 수신 포트 목록과 HTTP 앱 식별을 분리하고 진단을 추가했으며, 제한 시간은 늘리지 않았다. 새 Windows 분기는 다음 전체 CI로 확인한다. Mac 통과를 그 분기의 검증으로 간주하지 않는다.

두 번째 Windows 실행 [43782764443](https://github.com/sebia1993/aruba-airwave-ap-monitor/actions/runs/43782764443)은 EXE 컴파일과 desktop 검사 39 통과·1 Unix 제외를 확인했다. 공통 931개 중 925 통과·1 실패·5 플랫폼 제외이며 desktop 검사는 그 합계에 포함된다. 실패는 기존 `AcceptedVisibleRun_StillSurvivesBrowserCancellation`의 10초 Idle 대기였고, 당시 상태가 없어 원인은 미확정이다. 해당 테스트에 단계별 시간·상태 진단만 추가했고 기존 순서·판정·제한은 유지했다. macOS 대상 1개 통과와 진단 출력을 확인했다. 다음 Windows 실행에서는 한 검사 실패 후에도 독립 검사 결과를 수집하되, 모든 검사 성공 전에는 검증 ZIP을 업로드하지 않는다.

세 번째 Windows 실행 [43784351062](https://github.com/sebia1993/aruba-airwave-ap-monitor/actions/runs/43784351062)은 전체 실패했다. 공통 925 통과·1 실패·5 제외이며, 이번 실패는 `PauseDuringSeed_FinalizesThatSeedAndDoesNotBeginAnother`의 재개 후 Idle 10초 대기다. 재개 요청은 10.892초였고, 대기 종료 시 회차3은 Finalizing, 마지막 확정은 회차2, 저장 복구·저장 오류는 없었다. 이전 취소 검사는 통과했지만 그 이전 실패 원인이 소급 확정된 것은 아니다. Python은 12 통과·2 제외·1개 검사 실패(3개 하위 사례)로, 동일한 Windows 경로의 `RUNNER~1`과 `runneradmin` 문자열 차이를 잘못 비교했다.

같은 세 번째 실행에서 Windows 전용 9개, 네이티브 EXE 10개 사례, 실제 추출 ZIP의 기존 수집기·재시작·서비스·예약 작업·백업/복원 검사는 통과했다. EXE의 초기 Demo/Live 설정 화면 준비는 각각 1.536초/1.583초였으며, 별도 수집기 전체 확정은 최초 34.139초·재시작 16.914초였다. 이 개별 성공을 전체 Windows 통과로 표시하지 않는다. 전체 실패 때문에 검증 ZIP 업로드와 릴리즈 게시를 보류했으며, 경로 비교 수정과 수집 완료 대기 진단을 진행한다.

후속 검증 보정: 경로 검사는 존재하는 EXE·폴더의 실제 동일성과 미존재 데이터 경로의 상위 경로 정규화를 비교하며 데이터 미생성도 확인한다. 2,048대·실제 SQLite를 사용하는 Demo 선행 이력 통합 검사에는 임의의 10초 완료 성능 보장 대신 현재 프로필의 수집 한도(기본 120초)를 완료 대기 상한으로 적용한다. 조건 충족 즉시 끝나고 10초 경과·최종 상태를 기록하며 저장 복구 상태는 즉시 실패한다. 제품의 수집·결과 반영 제한, 5초 제어 게이트, 회차·결과 검증은 유지한다. 이는 기능 검사의 대기 기준 보정이며 성능 개선이나 이전 Windows 실패의 OS 원인 확정을 뜻하지 않는다. 새 전체 Windows CI 성공이 필요하다.

보정 후 macOS에서 Demo 선행 이력 통합 검사 12/12, Python 패키지 검사 15/15가 통과했다. 실제 PowerShell 경로 별칭 실험에서도 같은 파일·폴더와 미존재 데이터 경로를 올바르게 구분하고 다른 대상은 거부했다. Windows 8.3 경로와 변경된 통합 검사의 최종 근거는 다음 전체 Windows 실행으로 남긴다.

네 번째 Windows 실행 [43786596094](https://github.com/sebia1993/aruba-airwave-ap-monitor/actions/runs/43786596094), 소스 `b2263c8`, 역시 전체 실패했다. 공통 925 통과·1 실패·5 제외 중 유일한 실패는 기존 2,048대 전력 규모 검사였다. 실제 Power 저장이 5.366초에서 같은 취소 토큰의 `OperationCanceledException`으로 끝나고, 새 토큰의 중단 확정(0.239초) 후 Interrupted/Failed·표본0이 확인됐다. 이번 실패는 실제 5초 결과 반영 제한에 걸린 근거가 있으며, 앞선 Windows 실패에 그 원인을 소급 적용하지 않는다. 제한·대상 2,048대·기대 표본 12,288개는 유지하고 저장 경로의 병목을 조사한다.

네 번째 실행에서 보정한 Demo 선행 이력 12개는 모두 통과했고, 완료 대기 10회의 상한은 120초·실제 결과는 모두 Idle이었다(이번에는 10초 경과 사례 없음). Windows 전용 9개, Frontend 100개, Python 13 통과·Unix 2 제외, 실제 EXE·추출 ZIP 운영 검사도 통과했다. 최종 소스 `b2263c8`의 macOS 전체 재검증은 공통 931개·Frontend 100개·Python 15개 통과, Windows 전용 9개 Mac 제외, 빌드 경고·오류 0이었다. 전체 Windows 실패로 검증 ZIP 업로드와 릴리즈 게시는 진행하지 않았다.

전력 저장 보완은 해당 트랜잭션의 SQL 명령 재사용과 Power 저장 연결의 페이지 캐시 목표 16MiB로 한정했다. 12,288개 새 표본의 SQL 실행 98,304회를 준비된 명령 8개로 처리하며, 로컬 SQLite 계측에서 중간 페이지 쓰기는 62,605→17,875, 전체 페이지 쓰기는 63,039→21,442였다. 캐시 목표는 전체 메모리 상한이 아니며, 연결 종료 후 유지되지 않는다. WAL·FULL 동기화·정상 캐시 내보내기·5초 제한·표본 수·해시 형식·스키마는 유지했다. [명령 재사용 근거](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/bulk-insert), [페이지 캐시 계측 정의](https://www.sqlite.org/c3ref/c_dbstatus_options.html)

추가한 4개 검사는 빈 값 전환, 같은 작업 안 중복·시각 회귀, 오류 시 전체 되돌리기와 같은 회차 재시도를 확인한다. 보완 전후 모두 통과한 의미 보존 검사이며, 실패 재현 근거는 앞선 Windows의 5초 취소다. 관련 macOS 277개와 별도 실제 규모 검사 1개는 통과했다. 새 프로세스의 Power 적용은 보완 전 1.511초·후 1.531초였으므로 Mac 전체 속도 개선을 주장하지 않는다. Windows 효과는 전력 전용 진단과 기존 전체 Windows CI를 함께 실행해 판단하며, 전용 진단은 릴리즈 ZIP을 생성하지 않는다.

임시 계측을 제거한 보완 최종본의 macOS 전체 검증은 공통 935/935, Frontend 100, Python 15 통과, Windows 전용 9개 Mac 제외, 빌드 경고·오류 0으로 완료했다. 다음은 같은 소스의 전체 Windows CI·전용 전력 진단 및 성공한 원본 ZIP 검증이다.
