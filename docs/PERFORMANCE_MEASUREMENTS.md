# 합성 AP 2,000·5,000대 측정

## 저장 보완 후 측정 — ecca1d2

측정 소스는 `ecca1d2a20e26f7142dfba9de2d67cb18b716ce2`다. 추적 파일 변경이 없는 소스를 Release 빌드하고, 아래 네 조합을 각각 새 프로세스·빈 데이터 폴더에서 실행했다. macOS 27.2 Arm64, .NET 10.0.15의 합성 XML→실제 파서→SQLite 경로이며 실제 AirWave·Windows·HTTP 처리량 측정은 아니다. 변경 전 소스 `4d9a822`의 결과와 원시 JSON은 뒤에 별도로 보존한다.

`dotnet build tests/Performance -c Release` 후 다음 명령에서 `<시나리오>`를 `cycles` 또는 `steady-up`으로 지정한다. 생략하면 `cycles`다. `AIRWAVE_MEASUREMENT_COMMIT`은 실행자가 넣는 출처 정보이므로, 이번 측정에서는 별도 clean-source 기록 및 실제 실행 DLL 바이트의 SHA256도 대조했다.

```sh
AIRWAVE_MEASUREMENT_COMMIT=<소스 커밋> dotnet tests/Performance/bin/Release/net10.0/AirWaveApMonitor.Performance.dll <2000|5000> <새 출력 폴더> <시나리오>
```

- `cycles`: 기존과 같은 9회차다. 전체 Up→Down→미확인→공백 뒤 Down→복구→Down/Up 두 번으로 모든 대상의 반복 상태 변화를 확인한다.
- `steady-up`: 최초 Up 뒤 변경 없는 Up을 9번 반복하는 10회차다. 정상 사실·대상 집합 재사용을 직접 검사한다.
- 네 실행 모두 `checksPassed=true`. 매 회차 전체 목록을 500행씩 끝까지 읽어 고유 AP 수·상태·회차·집계를 검증했다. 사건/복구·과거 조회·새 저장소 객체로 재열기·온라인 백업·91일 정리 검사를 포함한다. 실제 프로세스 재시작 검증은 개발 기록과 구분한다.

### 정상 이력 재사용과 남은 증가 비용

정상 관측 facts와 membership은 재사용하지만 **DB 전체의 회차별 증가가 없어지는 것은 아니다.** 실행 시작·적용 당시 수동 등록/정책/배치 binding과 고정 대상 context에는 여전히 대상 수×회차 수에 따른 비용이 있다. 아래는 백업·정리 전 각 회차 완료 시 기록한 물리 크기다. 위 전체 결과의 최종 크기는 백업·정리 후 기록이며 SHM 포함 여부 때문에 마지막 회차 값보다 각각 32,768 B 작다.

| steady-up AP 수 | 최초 회차 bytes | 10번째 회차 bytes | 추가 9회차 증가 bytes | 후속 1회차 증가 범위 bytes |
|---:|---:|---:|---:|---:|
| 2,000 | 47,509,504 | 62,525,440 | 15,015,936 | 1,650,688–1,683,456 |
| 5,000 | 117,829,632 | 155,402,240 | 37,572,608 | 4,149,248–4,194,304 |

2,000대 DB의 읽기 전용 조사에서 `run_manual_bindings` 18,000행, `operations_applied_bindings` 20,000행이 확인됐다. 두 테이블+인덱스는 각각 6,221,824 / 6,856,704 B이며, `runs`+인덱스는 2,756,608 B다. 이번 자료는 수동값이 없어도 AP당 같은 188 B binding JSON을 반복하고, 후속 회차 context에는 약287,574 B의 고정 대상 2,000개를 보존한다. 최초 기준 등록 사건 12,000개는 모두 첫 회차에만 존재하며 이후 반복 변경 사건은 0이다. 최초 회차의 dbstat은 없어 각 테이블의 정확한 물리 증가량을 확정하지 않았다.

이 동결 근거의 의미를 보존하는 것은 필요하지만 매회 같은 JSON을 복제하는 형식 자체가 필수는 아니다. 남은 비용을 숨기거나 전체 DB가 일정 크기/O(1)라고 주장하지 않는다. 모든 AP가 Down/미확인이거나 상태가 바뀌면 필요한 상세·사건을 잘라내지 않는다. 장기 이력·인덱스·영구 사건 스냅샷·정상 백업 7개를 포함한 운영 디스크 요구량은 이 짧은 합성 실행으로 확정하지 않는다.

## 전력 표본 용량 — 실제 Demo 2,048대·3회

측정 소스는 위와 같은 `ecca1d2a20e26f7142dfba9de2d67cb18b716ce2`다. macOS에서 실제 앱의 수동 HTTP 요청→공유 수집 조정기→부가 runner→SQLite 경로로 연결 1회와 전력 3회를 실행했다. 자동 수집 간격은 60분으로 설정했고 아래 전력 세 회는 모두 수동 요청이다. 15분·30일 계산은 뒤의 별도 가정이다. 합성 Demo 자료이며 Live 부가 어댑터는 미구현·미검증·비활성이다.

[공개 측정 JSON](measurements/2026-11-16-enrichment-storage.json)에 다섯 시점의 전체 테이블 행 수·테이블/인덱스별 dbstat, 단계별 차분, 실제 수집 DTO·시각 및 실행 App/Core/Infrastructure DLL SHA256을 담았다. 원본은 보존하고 공개 복사본의 절대 데이터 폴더만 `synthetic-demo-data`로 바꿨다. 로컬 경로·요청 식별자·불필요한 health 정보는 공개 요약에서 제외했으며 원시 관측값/DB 파일을 내보내지 않았다. 이후 HTTP 응답 직렬화 보완이나 최종 Windows 빌드 결과를 이 측정 소스·DLL의 결과로 바꾸어 기록하지 않는다.

### 페이지·인덱스·백업 구분

마지막 시점의 주요 전력 테이블은 아래와 같다. 페이지 크기는 4,096 B이고 **페이지 bytes는 해당 테이블과 소속 인덱스 합계**다. 각 개별 인덱스와 나머지 모든 테이블 값은 공개 JSON에 있다.

| 테이블 | 행 수 | 페이지 bytes(인덱스 포함) | 이미 할당된 페이지 내부 unused bytes |
|---|---:|---:|---:|
| `power_samples` | 36,864 | 165,625,856 | 36,282,908 |
| `power_sample_keys` | 36,864 | 8,495,104 | 510,180 |
| `enrichment_power_current` | 12,288 | 3,776,512 | 294,647 |
| `enrichment_power_reads` | 36,864 | 2,322,432 | 74,277 |

전체 dbstat 페이지는 340,291,584 B, 그 안의 unused는 61,560,213 B다. unused는 페이지 내부 여유이며 DB 합계에 더하거나 물리 파일에서 곧바로 뺄 수 있는 별도 공간이 아니다. 다섯 시점 모두 freelist는 0페이지, `PRAGMA user_version`은 6이다. SQL 집계는 한 읽기 트랜잭션의 snapshot이고 파일 크기는 별도 stat 시점이다. WAL 0 / SHM 32,768 B는 관측 당시 값이며 최고 journal 크기 측정이 아니다. 초기 재시도의 읽기 전용 제공자가 만든 sidecar도 이 값에 포함된다.

백업 폴더는 매 시점 **2개 파일·692,658 B**로 DB 합계와 별도였다. 이는 기존 작은 백업 DB와 manifest이며 최종 DB의 정상 백업 7개 비용을 측정한 값이 아니다. 실제 운영은 정상 백업 7개·업데이트 전 별도 백업과 정리 작업 공간을 추가로 확보해야 한다.

### 15분·30일 산술 추정과 한계

모든 활성 대상 2,048대에서 여섯 지표를 매회 새 표본으로 얻는다고 가정하면 `2,048 × 6 × (24 × 60 ÷ 15) × 30 = 35,389,440`개다. 이는 **2,880회분의 산술 표본 수**이며 실제 저장한 표본은 3회·36,864개다. 실제 장비가 여섯 지표를 모두 제공한다는 뜻도 아니다.

관측한 세 증가량의 최소·최대를 그대로 2,880배 하면 **229,524,111,360–242,075,566,080 B (213.761–225.450 GiB)의 추가 증가**다. 이것은 초기 AP/연결 DB와 백업을 제외한 짧은 관측의 외삽이며 30일 실측·총 디스크 요구량이 아니다. 첫 회차의 초기 할당을 매번 반복한다고 계산하는 상한도 포함하므로 정상 상태의 성장 모델로 해석하지 않는다. raw 표본 외 상태·binding·조회/수용 이력·인덱스도 실제 증분에 포함된다.

원시 `power_samples`는 **조회 시각 `read_at_utc` 기준 30일** 뒤 정리한다. 자동 회귀의 31일 시계 이동에서 숫자 상세 만료와 영구 사건 근거 보존은 통과했지만, 이번 세 회의 실측은 30일 누적·정리를 수행하지 않았다. raw 만료가 식별 키·이력·영구 사건 복사본 또는 DB 전체의 30일 용량 상한을 뜻하지 않는다. 페이지 재사용, 인덱스와 장래 AP/사건 증가, WAL·백업 피크가 실제 디스크 사용량을 바꾼다. 정리 후 장기 파일 축소·운영 SLA, Windows·실제 AirWave/스위치·장기 현장 수집은 이 자료로 검증하지 않았다.

사건 스냅샷은 세 번의 전 AP Down→Up에서 생긴 사건 각각의 감지·복구 근거다. 이 영구 자료와 회차 사실은 90일 상세 정리 후에도 남는다. 2,000/5,000대 DB의 free list는 각각 1,167,360/2,924,544 bytes이며 재사용할 수 있지만, VACUUM 없이 파일 자체가 줄지는 않는다. 별도 백업은 DB와 같은 228,020,224/569,466,880 bytes이고 위 DB 크기에 포함하지 않았다.
