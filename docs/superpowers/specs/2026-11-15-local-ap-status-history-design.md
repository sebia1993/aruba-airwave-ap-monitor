# AirWave AP Monitor v0.1 — 로컬 AP 상태·장애 이력 설계 검토안

- 문서 상태: 검토 초안. 제품 구현 및 실환경 API 검증 완료를 의미하지 않는다.
- 작성일: 2026-11-15
- 저장소: https://github.com/sebia1993/aruba-airwave-ap-monitor
- 목표: 수집 PC 한 대에서 AirWave의 AP Up/Down을 자동 수집하고 장애·복구 관측 이력을 신뢰성 있게 보관한다.
- 설계 승인이 완료되면 이 문서를 기준으로 별도의 세부 구현 계획을 작성한다.

## 1. 확정된 요구사항과 설계자가 제안한 결정

### 사용자가 확정한 내용

1. 약 2,000대 이상의 AP를 일일이 확인하기 어려워 자동 수집과 이력 관리가 필요하다.
2. 24시간 켜둘 수 있는 사내 Windows 수집 PC가 있다.
3. 프로그램은 수집 PC에서만 사용한다.
4. 첫 버전은 AP Up/Down과 장애·복구 이력에 집중한다.
5. AirWave에는 HTTPS 웹으로 접근할 수 있으며, 사내 프록시/PAC 환경을 고려해야 한다.
6. 앞으로의 프로젝트 작업은 이 GitHub 저장소에서 관리한다.

### 이번 초안의 제안값 — 아직 사용자의 기술 선택으로 간주하지 않음

| 항목 | 제안 |
| --- | --- |
| 운영 대상 | 우선 AirWave 서버 1개, 수집 PC 1대, 운영자 1명 |
| 화면 | 수집 PC의 브라우저에서 여는 로컬 웹 화면 |
| 실행 | 수집과 로컬 조회 서버를 담당하는 백그라운드 EXE 1개 |
| 기술 | C# / .NET 10 LTS / ASP.NET Core / SQLite |
| 배포 대상 | Windows 11 x64, 런타임을 포함한 배포물 |
| 기본 수집 주기 | 5분, 설정 범위 1~60분 |
| 정상 관측 기준 | 해당 AP에 대해 유효한 is_up 값을 수신 |
| 추가 장애 확인 지연 | 기본적으로 추가하지 않음. 첫 유효 Down 관측을 기록 |
| 사건 이력 보존 | v0.1에서는 자동 삭제하지 않음 |
| 수집 실행 기록 | 90일, 운영 로그는 30일 |
| 원문 XML 저장 | 기본 비활성화 |
| 자동 백업 | 하루 1회, 성공한 최근 7개 로컬 DB 백업 유지 |

수집 주기와 요청 한도는 실제 AirWave 응답 크기·소요 시간과 원천 장비 상태 갱신 주기를 확인한 뒤 조정할 수 있다. 위 수치는 AirWave가 보장하는 한도나 이미 검증된 성능값이 아니다.

## 2. 해결하려는 문제와 첫 버전의 경계

### 성공 기준

- 운영자가 실행 버튼을 누르지 않아도 정해진 주기로 상태를 수집한다.
- 화면을 닫아도 수집이 계속된다.
- 특정 AP의 현재 관측 상태와 과거 장애·복구 이력을 찾을 수 있다.
- 통신 실패 때문에 AP 전체가 Down으로 기록되지 않는다.
- 같은 장애를 매번 새 장애로 생성하지 않으며, 재시작 후에도 사건이 이어진다.
- 실환경 연동이 실패한 상태를 정상 동작이나 검증 완료로 표시하지 않는다.

### v0.1 범위

- AP 기본 정보와 Up/Down 조회.
- AP별 장애 감지·복구 확인 이력.
- AP 이름/IP/MAC/폴더/상태/기간 검색 및 필터.
- 진행 중인 장애, 복구된 사건, 반복 Down 전환 횟수 조회.
- 사건에 대한 짧은 운영자 메모.
- 필터 결과의 CSV 내보내기.
- 수집 실패·미확인·목록 누락과 마지막 성공 시각 표시.
- 자동 시작, 로그 관리, DB 백업 및 업데이트 시 데이터 유지.

### 이후 버전으로 남기는 항목

- SSID 접속, 802.1X 인증, DHCP, 업무망 통신의 종단 간 검사.
- RF 품질·간섭·채널 최적화, 클라이언트 품질 분석.
- 장비 설정 변경, AP 또는 컨트롤러 재부팅.
- 여러 PC에서의 접속, 원격 사용자 관리, 외부 알림·티켓 시스템 연동.
- 실제 장애 발생·복구 시각을 전제로 하는 SLA/가용률/MTTR 보장.
- 설치 이전 장애 이력의 자동 복원.

## 3. 검토한 구현 방식

| 방식 | 장점 | 고려 사항 | 이번 초안의 판단 |
| --- | --- | --- | --- |
| 화면과 수집을 하나의 데스크톱 프로세스에 포함 | 실행 구조가 단순함 | 앱 종료나 로그오프가 수집 중단으로 이어지기 쉬움 | 지속 수집 목표의 기본안으로 채택하지 않음 |
| Windows 네이티브 화면 + 독립 수집기 | 일반 Windows 창으로 사용 | 화면과 수집기 사이 통신·배포 구성이 필요 | 사용 경험 선호에 따라 가능한 대안 |
| 로컬 웹 화면 + 백그라운드 EXE | 브라우저 종료와 수집을 분리하고 목록·이력 조회를 구성하기 좋음 | 로컬 포트와 프로세스 관리 필요 | 설계자 추천안 |

사용자는 로컬 전용 사용과 Up/Down 중심 범위를 선택했다. 브라우저 UI와 기술 스택은 위 추천안을 문서 검토의 기본으로 삼은 것이며, 별도의 사용자 확정 사실로 기록하지 않는다.

### 추천 구성

- 하나의 백그라운드 프로세스가 AirWave 수집, SQLite 기록, 로컬 조회 요청을 담당한다.
- 브라우저는 저장된 결과를 조회하며 브라우저 탭에서 수집 타이머를 실행하지 않는다.
- 웹 수신 주소는 127.0.0.1로 고정하고 기본 포트는 8765로 제안한다. 포트 변경은 가능하되 루프백 제한은 유지한다.
- 처음부터 수집기와 웹 서버를 여러 서비스로 나누지 않는다.
- 포트 충돌이나 DB 접근 실패로 시작하지 못하면 시작 실패를 명확히 기록한다.
- 프로그램 패키지와 영구 데이터 폴더를 구분한다.
- CSS·JavaScript·폰트 등 실행에 필요한 자원은 배포물에 포함한다.

## 4. AirWave 연동과 아직 남은 확인

공식 API의 기본 경로는 POST /LOGIN으로 세션 쿠키와 X-BISCOTTI 토큰을 받은 뒤 GET /ap_list.xml을 조회하는 방식이다.[S1]

현재 대화에서 실행한 진단은 인증서 검증 단계까지이며, 실제 로그인과 AP 목록 수신 성공은 확인되지 않았다. 인증서 이름, 신뢰 체인, 유효기간 관련 문제가 관측되었다. 주소·인증서·실행 계정 조건을 정리하고 실제 API 응답으로 어댑터를 검증해야 한다.

### 수집 원칙

1. 먼저 AP 목록을 일괄 조회한다. AP 2,000대에 개별 상세 조회를 반복하는 방식을 기본으로 삼지 않는다.
2. 세션 쿠키와 토큰은 실행 중 재사용하고, 프로그램을 재시작하면 다시 로그인한다.
3. HTTPS 인증서 검증을 유지한다. 전체 인증서 검증을 끄는 옵션은 v0.1 설계에 포함하지 않는다.
4. 자격 증명을 담은 요청을 다른 출처로 자동 리다이렉트하지 않는다.
5. 로그인 응답의 토큰·쿠키와 AP 목록 XML의 구조를 확인한다. HTTP 200만으로 성공으로 판단하지 않는다.
6. 서버 주소와 조회 범위를 포함한 수집 프로필의 식별자를 저장한다. 실행 시작 시 설정 버전을 고정하고, 진행 중 설정 변경은 해당 실행의 종료·반영 후 적용한다.
7. 폴더·그룹 필터가 필요하면 실제 API에서 동작을 확인한 필터만 사용한다.
8. AP 범위는 device_category 등 실제 응답의 분류를 확인하여 정한다. 컨트롤러·스위치를 AP로 합산하지 않는다.

### 서버와 조회 범위의 변경

- 서버 주소는 HTTPS 출처(스킴·호스트·포트)로 정규화하며 경로·사용자 정보·쿼리·프래그먼트는 허용하지 않는다.
- 서버의 출처가 바뀌면 기본적으로 새로운 AirWave 인스턴스 데이터셋을 만든다. 기존 사건은 기존 데이터셋에 보존하고 추적 종료 사유를 남긴다.
- 동일 서버의 IP를 FQDN으로 바꾸는 경우에도 v0.1은 이전 데이터셋을 자동 병합하지 않는다. 최초 실제 수집 전에 사용할 정식 주소를 확정한다.
- 자격 증명은 프로필과 서버 출처에 연결한다. 출처가 바뀌면 세션을 폐기하고 자격 증명을 다시 등록한다.
- AirWave DB 재구축·복원 등으로 AP ID의 의미가 바뀐 경우 새 데이터셋으로 시작한다. 이를 완전히 자동 감지한다고 가정하지 않는다.
- 같은 서버의 조회 범위나 로그인 계정이 바뀌면 범위 버전을 올리고 대수를 다시 확인한다. 이전 버전으로 요청한 응답을 새 범위의 누락·제외 판단에 사용하지 않는다.

### 프록시와 실행 계정

기본값은 실행 계정의 Windows 설정을 따르는 방식이다. Windows의 .NET 기본 프록시는 환경변수가 있으면 이를 먼저 사용하고, 그렇지 않으면 사용자 프록시 설정을 사용한다.[S2]

- 수동 실행 계정과 자동 수집 계정의 환경을 각각 검증한다.
- PAC URL과 고정 프록시 주소를 같은 입력값으로 취급하지 않는다.
- 진단 결과에는 선택한 연결 경로, TLS 결과, HTTP/API 결과를 구분한다.
- 인증서 신뢰 및 자격 증명 복호화도 실제 수집 계정에서 확인한다.
- 환경 설정을 자동으로 변경하거나 임의의 인증서를 신뢰 저장소에 등록하지 않는다.

### 요청과 실패 제어의 제안값

- HTTP 요청 1회의 제한 시간: 45초.
- 수집 1회의 전체 제한 시간: 120초. 로그인·세션 갱신도 이 한도에 포함한다.
- 응답 크기 제한: 압축 해제 후 64 MiB. 한도를 넘으면 명시적 실패로 기록한다.
- 수집은 한 번에 하나만 실행한다. 수동 조회도 같은 실행 잠금을 사용한다.
- 실행 중 다음 주기가 도래하면 요청을 중첩하거나 쌓아 두지 않고 건너뛴 횟수를 기록한다.
- 일시적인 통신 실패는 다음 예정 주기에 재시도한다. 한 주기 안에서 반복 재시도하지 않는다.
- API의 401 또는 확인 가능한 동일 출처 로그인 화면 전환 등 세션 만료 증거가 있으면, 한 주기 안에서 재로그인과 재조회를 최대 한 번만 시도한다.
- API의 403은 권한·토큰 문제로 분류하고 무조건 재로그인하지 않는다.
- 로그인 거절 또는 세션 재인증 실패가 확인되면 자동 로그인 시도를 멈추고 자격 증명 확인이나 사용자의 명시적 재시도를 기다린다.
- TLS·네트워크·인증·권한·응답 형식·데이터·저장 실패를 서로 다른 오류 범주로 기록한다.

## 5. 데이터의 상태와 최신성

AP가 마지막으로 보고한 상태와 프로그램이 그 상태를 확인한 품질을 분리한다.

| 구분 | 예 |
| --- | --- |
| 마지막 유효 AP 상태 | Up, Down, 아직 유효 상태 없음 |
| 관측 품질 | 이번 수집에서 확인, 수집 실패, 응답에서 누락, 상태값 불명, 일정 시간 갱신 없음 |
| 수집 실행 결과 | 성공, 일부 데이터만 유효, 실패, 재시작으로 중단됨 |
| 관리 대상 여부 | 현재 조회 대상, 조회 범위에서 제외, 식별 정보 변경으로 추적 종료 |

### 수집 실패 처리

- 마지막으로 유효하게 받은 AP 상태와 그 시각을 보존한다.
- 전체 조회가 실패하면 현재 Up/Down을 새로 확인한 것처럼 집계하지 않는다.
- 화면은 최신 확인이 불가능함을 먼저 보여 주고, 필요하면 마지막 성공 시점의 대수를 별도 표기한다.
- 기존 진행 중 장애를 자동 종료하거나 새 장애를 만들지 않는다.
- 기본 주기의 2배 이상 유효 관측이 없으면 갱신 지연 표시를 추가한다. 이는 통신 장애 확정 조건이 아니다.

### 목록 누락과 불완전 응답

- 비정상 XML, 잘못된 루트, 로그인 HTML, 응답 크기 초과는 전체 수집 실패다.
- 문서 구조는 정상이지만 일부 AP의 ID·상태값이 잘못됐으면 해당 레코드는 상태 판정에서 제외하고 실행 결과를 부분 유효로 기록한다.
- 중복 AP ID는 어느 레코드가 맞는지 임의로 선택하지 않는다. 충돌한 ID 전체를 이번 판정에서 제외한다.
- 부분 유효 응답에서도 식별과 상태가 검증된 AP는 관측을 반영할 수 있다. 전체 수집 정상으로 표시하지 않는다.
- 누락·불명 상태·중복 ID로 제외된 AP는 각각 관측 공백으로 기록한다. 다른 AP의 수집이 성공해도 해당 AP의 공백을 닫지 않는다.
- 부분 유효 실행은 검증된 AP의 최종 관측 시각만 갱신한다. 전체 수집 성공 시각은 모든 기대 대상에 유효한 관측이 있을 때만 갱신한다.
- 누락된 AP는 Down이나 삭제로 단정하지 않는다. 마지막 상태와 마지막 관측 시각을 유지하면서 확인 대상으로 표시한다.
- 최초 조회가 0대이거나 기존 대상이 있는데 0대가 반환되면 대상·권한·응답 확인이 필요한 결과로 표시한다.
- 조회 범위가 바뀌면 범위 변경 이력을 남긴다. 이전 범위에서 빠진 AP의 사건을 복구된 것으로 처리하지 않는다.
- 현재 범위에서 이전에 확인한 추적 대상은 기대 대상 목록에 유지한다. 누락 대상의 추적 종료는 운영자가 사유를 남겨 명시적으로 확인하며, 사건과 과거 기록은 보존한다.
- 조회 범위 버전이 바뀌면 새 범위의 기준 목록을 별도로 수립하고 이전 범위의 제외 상태를 구분한다. 범위 변경 자체가 AP 장애·복구 사건을 만들지 않는다.

### 시각의 의미

- 프로그램이 응답을 관측한 시각과 AirWave last_contacted 값을 따로 저장한다.
- last_contacted는 AirWave 원천 정보이며 장애 시작·복구 시각으로 대체하지 않는다.
- Down인 AP의 last_contacted가 오래됐다는 사실만으로 프로그램의 수집 실패를 선언하지 않는다.
- 시각은 UTC로 저장하고 화면은 한국 표준시로 표시한다.
- 순서는 수집 실행의 증가하는 식별자로 보존한다. PC 시계 역행으로 시각이 뒤집히면 음수 장애 시간을 표시하지 않고 시간 확인 필요로 남긴다.
- AirWave의 원천 갱신 주기와 프로그램 수집 주기에 따른 감지 지연이 있다. 관측 사이에 발생했다가 복구된 짧은 장애를 모두 기록한다고 보장하지 않는다.

## 6. AP 식별과 장애·복구 사건

### AP 식별

- 기본 연결 키는 AirWave 인스턴스 식별자 + AirWave AP ID다.
- 이름과 IP는 바뀔 수 있는 속성이므로 장비 식별 키로 사용하지 않는다.
- 일련번호와 LAN MAC은 응답에 있을 때 보조 식별 정보로 저장한다.
- 다른 AP ID를 가진 기록을 이름·IP가 같다는 이유로 자동 병합하지 않는다.
- 동일 AP ID에서 기존에 확인된 하드웨어 식별자가 바뀌면 새 장비 세대로 분리한다. 비교 우선순위는 일련번호, 일련번호를 사용할 수 없을 때 LAN MAC이다.
- 보조 식별자가 응답에서 빠진 것만으로 교체로 판단하지 않는다.
- 장비 세대가 바뀐 경우 기존 열린 사건은 추적 종료 사유를 남기고 복구 시각을 만들지 않는다.
- 장비 세대 분리를 상태 전환보다 먼저 적용한다. 새 세대의 이전 상태는 없음이며, 교체 장비의 Up을 구장비 장애의 복구로 기록하지 않는다.
- 중복 ID로 제외한 레코드는 상태 판정뿐 아니라 식별 정보·장비 세대 변경에도 사용하지 않는다.

### 상태 전환 규칙

| 이전에 유효하게 관측한 상태 | 이번 유효 상태 | 처리 |
| --- | --- | --- |
| 없음 | Up | 기준 상태 등록. 복구 사건 생성 없음 |
| 없음 | Down | 최초 확인 당시 Down 사건 생성. 실제 시작 시각 미상 표시 |
| Up | Down | 새 장애 사건 1개 생성 |
| Down | Down | 같은 열린 사건의 마지막 Down 관측 갱신 |
| Down | Up | 기존 사건에 첫 복구 확인 시각 기록 |
| Up | Up | 현재 관측 갱신. 장애 사건 생성 없음 |
| 어느 상태든 | 이번 관측 불가 | AP 상태 전환·복구 없음. 관측 품질과 수집 결과만 변경 |

- 기본 정책은 한 번의 유효 관측을 반영하는 것이다. 추가로 두 번 Down을 기다리는 규칙을 고정하지 않는다.
- 현재 장비 세대마다 열린 장애 사건은 최대 하나다.
- 재시작 후 DB의 마지막 상태와 열린 사건을 복원한다.
- 수집 중단 구간을 거쳐 다시 관측한 경우 해당 사건에 관측 공백이 있었다는 표시를 남긴다.
- Up → 관측 공백 → Down은 새 사건을 만들되 마지막 Up과 첫 Down 사이에 공백이 있음을 함께 기록한다.
- Down → 관측 공백 → Down은 같은 열린 사건을 유지하지만, 공백 동안 계속 Down이었다고 단정하지 않는다.
- Down → 관측 공백 → Up은 재개 후 첫 Up 시각을 복구 확인 시각으로 기록하고 실제 복구 시각은 알 수 없음을 표시한다.
- 조회 범위를 벗어난 열린 사건은 추적 중지로 표시해 현재 감시 대상 집계에서 분리한다. 다시 대상이 되면 공백을 표시하고 관측을 이어간다.
- 운영자 메모는 자동 상태와 독립적인 부가 정보다. 메모 입력으로 AP를 Up 처리하거나 사건을 복구 완료로 바꾸지 않는다.

### 사건에 남길 최소 정보

- 내부 사건 ID, 내부 AP 식별자, AirWave 인스턴스/AP ID, 장비 세대.
- 당시 AP 이름·IP·폴더 등 조회에 필요한 식별 정보.
- 마지막 Up 관측, 첫 Down 관측, 마지막 Down 관측, 첫 복구 확인 시각.
- 최초 관측 시 이미 Down인지, 관측 공백이 있었는지, 추적 중지·종료 사유.
- 사건 상태: 관측 중, 복구 확인, 추적 종료. 별도로 추적 일시 중지 여부.
- 운영자 메모와 메모 수정 시각.

화면의 시간 항목은 장애 감지 시각, 복구 확인 시각, 감지 후 경과시간 또는 감지~복구 확인 간격으로 표시한다. 정확한 서비스 중단 시간으로 표현하지 않는다. 반복 장애 횟수는 확인된 Up → Down 전환 횟수로 정의하고, 최초 확인 당시 Down인 건은 따로 구분한다.

## 7. 저장, 보존, 백업

### 논리 데이터 구성

| 데이터 | 목적 |
| --- | --- |
| 수집 프로필 | 서버 식별자, 주소, 조회 범위, 주기, 설정 버전 |
| AP 및 현재 관측 | 식별 정보, 마지막 유효 상태, 관측 시각, 원천 시각, 품질 |
| 수집 실행 기록 | 시작·종료 시각, 결과, 조회·유효·오류 건수, 오류 범주, 소요 시간 |
| 장애 사건 | 감지·복구, 중복 방지, 최초 관측 Down, 공백 및 추적 상태 |
| AP 변경 기록 | 이름·IP·소속·식별 정보의 변경 |
| 관측 공백 기록 | 통신 실패, 프로세스 중단, 범위 변경 등으로 확인하지 못한 구간 |
| 메모 | 사건에 연결된 운영자 텍스트 |
| 스키마 버전 | 업데이트·마이그레이션 상태 |

- 상세 테이블명과 코드 인터페이스는 승인 후 구현 계획에서 정한다.
- 한 수집 실행에서 검증된 AP의 현재값, 장비 세대·사건 전환, AP별 공백, 실행의 최종 결과·건수와 성공 시각을 하나의 DB 트랜잭션으로 저장한다.
- 실행 시작 기록은 별도로 먼저 저장할 수 있다. 최종 반영에는 실행 ID별 중복 방지 제약을 두어 같은 실행을 두 번 적용하지 않는다.
- 저장 실패 시 부분 반영을 롤백하고 마지막 성공 시각을 갱신하지 않는다.
- 프로세스 중복 실행 방지와 DB 제약으로 중복 사건을 방지한다.
- SQLite는 로컬 디스크에 두고 WAL 모드를 사용한다. 쓰기는 백그라운드 프로세스에서 직렬화한다.[S3]
- DB·설정·비밀 저장 파일·로그는 실행 파일 교체 위치와 분리한 영구 데이터 디렉터리에 둔다.
- 기본 데이터 위치는 %ProgramData%\AirWaveAPMonitor로 제안하며 실제 실행 계정에 필요한 접근 권한을 부여한다.

2,000대를 5분마다 모두 누적하면 하루 576,000행, 30일에 17,280,000행이 된다. 이는 2,000 × 288 × 30의 계산이며 용량 실측 결과가 아니다. v0.1은 현재값을 갱신하고 변경 사건 및 실행 기록을 보관한다.

### 보존과 백업 정책 제안

- 장애 사건, 메모, AP 변경 기록: 자동 삭제 없음.
- 수집 실행 및 관측 공백 상세 기록: 90일. 사건에 남은 공백 표시는 상세 기록이 만료돼도 유지.
- 운영 로그: 30일, 파일 크기 제한과 순환 보관.
- 원문 API 응답: 기본 저장 안 함.
- DB 온라인 백업 API를 이용해 하루 한 번 백업하고 성공 검증된 최근 7개를 보관한다.[S4]
- 업데이트 전에는 별도 백업을 만든다. 실패한 새 백업 때문에 기존 정상 백업을 먼저 지우지 않는다.
- 복원은 수집기를 정지한 상태에서 스키마와 DB 무결성을 확인한 뒤 수행한다.
- 복원 후에는 재개 시점까지의 관측 공백을 표시한다.
- 같은 PC의 백업은 프로그램 업데이트·DB 복원용이며 PC 저장장치 자체의 손실까지 보장하지 않는다.

## 8. 화면에서 할 수 있어야 하는 작업

구체적인 배치와 시각 디자인은 별도 화면 검토로 정한다. 다음은 화면 기능 요구사항이다.

1. 현황: 관측 기준 시각, 수집 상태, 마지막으로 유효한 Up/Down 대수, 이번에 확인하지 못한 대상.
2. AP 목록: 이름/IP/MAC/폴더/그룹/컨트롤러/상태/최종 관측으로 검색·정렬·페이지 조회.
3. AP 상세: 현재 정보와 장애·복구 사건을 시간순으로 조회.
4. 사건 목록: 진행 중/복구 확인/추적 종료, 기간, AP 조건으로 조회.
5. 수집 기록: 마지막 성공, 오류 범주, 다음 실행 예정, 조회 건수와 소요 시간.
6. 설정·진단: 서버 주소, 자격 증명 등록, 수집 주기, 조회 범위, 연결 진단.
7. CSV 내보내기: 화면의 필터 조건과 관측 시각을 포함. 한글 Excel 사용을 고려한 UTF-8 BOM 및 수식으로 해석될 수 있는 값 처리.
8. 누락 대상 확인: 실제 관리 대상에서 빠진 AP의 추적 종료와 사유 기록. 과거 이력을 삭제하거나 복구로 바꾸지 않는다.

수집 중지와 브라우저 닫기는 서로 다른 동작이다. 수집이 중지되어도 기존 이력은 조회할 수 있어야 한다.

## 9. 실행·인증정보·로컬 접근

### 자동 실행

- Windows 서비스로 백그라운드 EXE를 운영하는 방식을 우선 제안한다.[S5]
- 동일 실행 파일의 대화형 실행도 진단과 초기 확인을 위해 제공한다.
- 서비스 설치를 사용할 수 없으면 동일 수집기의 작업 스케줄러 실행을 배포 대안으로 검토한다.
- 실제 채택할 자동 실행 방식과 실행 계정은 사내 PC의 권한·정책 확인 후 배포 전에 결정한다.
- 서비스나 예약 작업 설정은 설치 절차에서 명시적으로 수행한다. 앱 첫 실행이 임의로 시스템 설정을 변경하지 않는다.
- 실제 운영 완료 기준에는 선택한 방식으로 재부팅 후 수집이 재개되는지 확인하는 항목을 포함한다.
- 예약 작업을 선택하면 실행 제한 시간, 중복 실행, 로그온 여부와 네트워크 자격 증명 조건을 확인한다.

### 자격 증명

- AirWave 자격 증명은 설정·진단 화면에서 입력하고, 실제 수집기 실행 계정 범위의 Windows DPAPI로 보호하여 저장한다.[S6]
- 브라우저는 보호된 파일을 직접 읽지 않으며, 백그라운드 프로세스가 등록과 복호화를 담당한다.
- 실행 계정이 바뀌거나 복호화가 실패하면 자격 증명을 다시 등록해야 한다.
- 쿠키와 X-BISCOTTI 토큰은 메모리에 보관하고 일반 로그·CSV·백업 문서에 출력하지 않는다.
- DB 백업을 다른 PC에 복원하면 자격 증명을 다시 등록한다.

### 로컬 웹 접근

- 이 초안은 운영자 한 명이 신뢰하는 Windows 사용자 환경에서 사용하는 것을 전제로 한다. 같은 PC의 서로 신뢰하지 않는 계정을 격리하는 앱 로그인·권한 모델은 포함하지 않는다.
- 루프백은 네트워크 접근 범위 제한이며 사용자 인증을 대체하지 않는다. 공용 PC의 계정별 격리가 필요해지면 구현 전에 접근 모델을 다시 정한다.
- 루프백에만 바인딩하고 허용된 Host와 동일 출처 요청을 확인한다.
- 변경 요청에는 위조 요청 방지 토큰을 적용하고 GET 요청으로 설정·상태를 변경하지 않는다.
- CORS를 외부 출처에 개방하지 않는다.
- 일반 사용자 비밀이나 내부 데이터가 외부 리소스 요청으로 전송되지 않도록 모든 UI 자원을 로컬에서 제공한다.
- 실제 주소, 계정, 인증서, AP 목록, DB, 실행 로그는 GitHub에 저장하지 않는다. 공개 저장소에는 가상 예제 데이터만 둔다.

| 단계 | 산출물 | 통과 기준 |

| 0. 설계 검토 | 이 설계 문서와 검토 기록 | 요구 범위와 제안값을 검토하고 구현 기준 확정 |
| 1. 연결 어댑터 | 진단, 로그인, AP 목록 파싱 | 샘플 검증과 실제 수집 계정의 API 확인을 구분하여 기록 |
| 2. 상태·사건 저장 | 현재 상태, 사건, 수집 실행 기록 | 상태 전환·실패·누락·공백·재시작 기준 충족 |
| 3. 로컬 조회 | 현황, 목록, 상세, 필터, CSV, 메모 | 필요한 AP와 기간의 기록 조회 가능 |
| 4. 상시 운영 | 자동 시작, 백업, 로그, 배포물 | 선택한 운영 방식에서 재부팅 후 수집 재개 및 이력 유지 |
| 5. 운영 확인 | 실제 AirWave 비교 결과 | 조회 범위·대수·상태·장애 이력이 실제 환경과 일치하는지 사용자 확인 |

실환경 API 연결이 미해결이어도 가상 응답을 이용한 파싱·상태 처리·저장·화면 개발은 가능하다. 실환경 확인 항목은 별도 상태로 남기며 완료로 계산하지 않는다.

### 실환경에서 확인할 전제

- 연결 확인 전: 정식 HTTPS 주소, 인증서 이름·신뢰·유효기간, 실제 계정의 API 인증 방식과 조회 범위.
- 배포 전: Windows 버전·CPU 아키텍처, 자동 시작 방식의 허용 여부, 실행 계정과 데이터 폴더 접근 권한.
- 운영 확인 전: 동일 실행 계정에서의 프록시·인증서·자격 증명 복호화, 재부팅 후 재개, 실제 AirWave와 대수·상태 비교.
- 이 항목은 실환경 완료 기준이다. 아직 확인하지 않은 값을 확인 완료로 가정하거나 제품 검증 완료율에 포함하지 않는다.

### 의미 있는 검증 시나리오

- Up → Down → Down → Up: 장애 1건과 복구 1회.
- 처음 확인할 때 Down: 실제 시작 시각 미상, 복구 시 첫 Up 관측 기록.
- Up → 수집 실패: 새 Down 사건 없음, 현재 상태를 새로 확인했다고 표시하지 않음.
- Down → 수집 실패 → 재시작 → Down → Up: 중복 사건 없음, 관측 공백 표시.
- 정상 XML 일부 누락·불명 상태·중복 ID·0건: 대량 장애/삭제 오판 없음.
- 로그인 HTML을 반환하는 HTTP 200: AP 목록 성공으로 판정하지 않음.
- 세션 만료와 잘못된 비밀번호: 제한된 재인증과 반복 로그인 중단.
- 수집과 DB 저장 도중 프로세스 종료: 재시작 후 부분 사건이나 중복 사건 없음.
- AP 이름/IP 변경, 하드웨어 식별자 변경, 조회 범위 변경: 이력 대상과 추적 상태 유지.
- PC 시각 역행: 음수 시간이나 잘못된 관측 순서 표시 없음.
- 2,000대 및 5,000대 가상 목록: 정확한 파싱·집계, 수집 중첩 없음, 자원 사용량 측정.
- 선택한 운영 계정에서 프록시/TLS/API 확인, 브라우저 종료와 재부팅 후 수집 유지.
- DB 백업·복원과 실행 파일 교체 후 이력 유지.
- 저장 공간 부족·읽기 전용 DB: 저장 실패 표시, 성공으로 위장하지 않음.

## 11. 구현 계획 작성자에게 맡기는 부분

- 상세 클래스·인터페이스·테이블 이름과 파일 분리.
- UI의 구체적인 배치와 스타일.
- 검사·빌드 도구의 세부 구성과 패키지 고정 버전.
- 날짜·크기·상태값 입력 검증의 코드 구조.
- 테스트용 가상 데이터 생성 방법과 성능 측정 도구.

위 선택은 이 문서의 상태 처리 규칙, 실행 범위, 데이터 보존 약속을 변경하지 않는 범위에서 정한다.

## 12. 검토 상태

- 요구사항 확인: 로컬 전용, 자동 수집, Up/Down과 장애·복구 이력 중심 범위 확정.
- 기술·기본값: 이번 초안의 설계자 제안이며 사용자 최종 검토 대상.
- 독립 설계 검토: 구현 계획 작성 관점의 검토와 상태·이력 일관성 검토를 수행했다.
- 반영한 보완: 실행 전체의 원자적 저장, AP별 관측 공백, 실행 중 설정 버전 고정, 장비 세대 우선 처리, 서버 출처와 자격 증명의 연결, 로컬 접근의 신뢰 범위.
- 중요한 미해결 설계 질문: 검토 시점에 추가로 발견되지 않음. 기술·기본값의 사용자 검토와 실환경 전제 확인은 별도 단계다.
- 제품 구현: 아직 시작하지 않음.
- 실환경 API 성공: 아직 확인되지 않음.
- 다음 산출물: 설계 검토 후 작업 단위와 검증 기준을 담은 세부 구현 계획.
