# AirWave AP Monitor v0.1 — 로컬 AP 상태·운영 이력 설계 검토안

- 문서 상태: 이력·저장 항목 확대를 사용자 요청으로 반영한 설계 초안. 기술 기본값, PoE·LLDP 데이터 제공 범위는 아래의 확인 상태를 따른다. 제품 구현 및 실환경 API 검증 완료를 의미하지 않는다.
- 작성일: 2026-11-15
- 저장소: https://github.com/sebia1993/aruba-airwave-ap-monitor
- 핵심 목표: 수집 PC 한 대에서 AirWave를 주기적으로 조회하여 Down AP 현황을 추적하고, 신규 Down·미복구·복구·반복 이력을 확인한다. 기본정보·연결·교체·펌웨어·컨트롤러·작업 이력은 이 감시와 조사를 지원한다.
- 설계 승인이 완료되면 이 문서를 기준으로 별도의 세부 구현 계획을 작성한다.

## 1. 확정된 요구사항과 설계자가 제안한 결정

### 사용자가 확정한 내용

1. 약 2,000대 이상의 AP를 일일이 확인하기 어려워 자동 수집과 이력 관리가 필요하다.
2. 24시간 켜둘 수 있는 사내 Windows 수집 PC가 있다.
3. 프로그램은 수집 PC에서만 사용한다.
4. 첫 버전의 중심은 AP Up/Down과 장애·복구 이력이다. 이후 사용자의 전체 반영 요청으로 아래 운영 이력과 저장 항목을 포함한다.
5. AirWave에는 HTTPS 웹으로 접근할 수 있으며, 사내 프록시/PAC 환경을 고려해야 한다.
6. 앞으로의 프로젝트 작업은 이 GitHub 저장소에서 관리한다.
7. 2026-11-15 사용자가 제안 항목의 전체 반영을 요청했다. AP 식별·위치·컨트롤러·모델·펌웨어·관리 상태, 연결 정보의 출처·확인 시각, 변경 전후 값, 장애 당시 정보, AP 교체, 작업·조치 이력을 설계 범위에 포함한다.
8. 사용자가 프로젝트의 목적을 주기적 감시를 통한 Down AP 현황 추적으로 다시 명확히 했다. 이미 승인된 이력·저장 범위는 유지하되 Down 감시 기능의 개발·운영을 우선한다.

같은 요청에서 AP 연결 스위치, 전력, LLDP 유지 상태의 확인 가능성을 질문했다. 이 문서는 해당 항목을 데이터 제공 여부에 따라 활성화하는 수집·표시 대상으로 설계하되, 공식 문서상 화면 기능과 실환경 API 제공 여부를 구분한다. 전체 반영 요청은 기능·이력 항목에 대한 승인으로 기록하며, 기술 스택이나 모든 API 필드의 확보 완료로 해석하지 않는다.

## 2. 해결하려는 문제와 첫 버전의 경계

### 핵심 운영 흐름과 우선순위

- 운영자는 프로그램을 열어 이번에 Down으로 확인한 AP, 지난번에 Down이었으나 이번에는 확인하지 못한 AP, 새 Down, 복구 확인, 장기 미복구를 구분할 수 있어야 한다.
- AP 기본 조회 → 상태·사건·회차별 현황 저장 → Down 목록과 변화 조회 → 재시작 후 자동 수집 유지 순서로 핵심 감시를 먼저 완성한다.
- 스위치·포트 등 이미 확보되는 정보는 Down 목록과 조사에 활용한다. PoE·LLDP의 추가 API 검증, 상세 자산·작업 화면의 완성은 핵심 감시의 착수·사용 조건으로 삼지 않는다.
- 이는 승인된 부가 이력을 삭제하거나 전체 프로젝트 완료로 간주하는 범위 축소가 아니다. 핵심 감시와 보조 기능의 개발 순서·완료 상태를 따로 관리한다.

### 성공 기준

- 운영자가 실행 버튼을 누르지 않아도 정해진 주기로 상태를 수집한다.
- 화면을 닫아도 수집이 계속된다.
- 특정 AP의 현재 관측 상태와 과거 장애·복구 이력을 찾을 수 있다.
- 통신 실패 때문에 AP 전체가 Down으로 기록되지 않는다.
- 같은 장애를 매번 새 장애로 생성하지 않으며, 재시작 후에도 사건이 이어진다.
- AP 이름·IP·연결 위치가 바뀌거나 AP가 교체되어도 이전 사건의 장비·연결 정보가 유지된다.
- 자동 관측 사실, 운영자가 입력한 작업 사실, 미확인·오래된 정보를 구분한다.
- 실환경 연동이 실패한 상태를 정상 동작이나 검증 완료로 표시하지 않는다.
- 특정 수집 회차의 Down 대수·해당 AP 목록·확인 불가 대상을 현재 정보의 변경과 무관하게 조회할 수 있다.
- 핵심 화면에 수집 기준 시각과 이번 유효 Down, 마지막 Down이나 이번 미확인인 AP를 구분하여 표시한다.

### v0.1 범위

- AP 이름·IP·유선 MAC·시리얼·모델·펌웨어·위치·폴더·그룹·컨트롤러·관리 상태와 Up/Down 조회.
- AP별 장애 감지·복구 확인 이력.
- 수집 회차별 현황 요약, Down AP 목록, 신규·기존 미복구·최초 Down·복구 확인 분류와 확인 불가 목록.
- AP 기본정보, 스위치·포트 연결, 펌웨어·컨트롤러 변경의 이전값·새값·감지 시각·출처 기록.
- AP 장비 교체와 설치 지점별 배치 이력. 장비별 이력과 같은 지점의 연속 이력을 구분.
- 장애 감지·복구 확인 시점에 이미 확보한 마지막 유효 장비·연결 정보의 불변 스냅샷.
- AP·설치 지점·스위치·포트·상태·관리 상태·기간·이력 종류별 검색 및 필터.
- 진행 중인 장애, 복구된 사건, 반복 Down 전환 횟수 조회.
- 점검·계획 작업·현장 조치의 일시·내용·결과·메모와 수정 기록. 자동 사건과 연결 가능.
- 자동 수집되지 않는 위치·대장 정보의 직접 입력 및 CSV 가져오기. 관측값과 수동 등록값의 출처 분리.
- 스위치 포트 상태·PoE·이웃 관측의 저장 및 표시 구조. 자동 수집은 해당 모델·계정·API에서 제공되는 항목만 활성화.
- 필터 결과의 CSV 내보내기.
- 수집 실패·미확인·목록 누락과 마지막 성공 시각 표시.
- 자동 시작, 로그 관리, DB 백업 및 업데이트 시 데이터 유지.

### 이후 버전으로 남기는 항목

- SSID 접속, 802.1X 인증, DHCP, 업무망 통신의 종단 간 검사.
- RF 품질·간섭·채널 최적화, 클라이언트 품질 분석.
- 장비 설정 변경, AP 또는 컨트롤러 재부팅.
- 여러 PC에서의 접속, 원격 사용자 관리, 외부 알림·티켓 시스템 연동.
- 실제 장애 발생·복구 시각을 전제로 하는 SLA/가용률/MTTR 보장.
- 설치 이전 장애 이력의 자동 복원.

## 3. 검토한 구현 방식

| 방식 | 장점 | 고려 사항 | 이번 초안의 판단 |
| --- | --- | --- | --- |
| 화면과 수집을 하나의 데스크톱 프로세스에 포함 | 실행 구조가 단순함 | 앱 종료나 로그오프가 수집 중단으로 이어지기 쉬움 | 지속 수집 목표의 기본안으로 채택하지 않음 |
| Windows 네이티브 화면 + 독립 수집기 | 일반 Windows 창으로 사용 | 화면과 수집기 사이 통신·배포 구성이 필요 | 사용 경험 선호에 따라 가능한 대안 |
| 로컬 웹 화면 + 백그라운드 EXE | 브라우저 종료와 수집을 분리하고 목록·이력 조회를 구성하기 좋음 | 로컬 포트와 프로세스 관리 필요 | 설계자 추천안 |

사용자는 로컬 전용 사용과 Up/Down 중심의 운영 이력 범위를 선택하고 제안한 이력·필드의 전체 반영을 요청했다. 브라우저 UI와 기술 스택은 위 추천안을 문서 검토의 기본으로 삼은 것이며, 별도의 사용자 확정 사실로 기록하지 않는다.

### 추천 구성

- 하나의 백그라운드 프로세스가 AirWave 수집, SQLite 기록, 로컬 조회 요청을 담당한다.
- 브라우저는 저장된 결과를 조회하며 브라우저 탭에서 수집 타이머를 실행하지 않는다.
- 웹 수신 주소는 127.0.0.1로 고정하고 기본 포트는 8765로 제안한다. 포트 변경은 가능하되 루프백 제한은 유지한다.
- 처음부터 수집기와 웹 서버를 여러 서비스로 나누지 않는다.
- 포트 충돌이나 DB 접근 실패로 시작하지 못하면 시작 실패를 명확히 기록한다.
- 프로그램 패키지와 영구 데이터 폴더를 구분한다.
- CSS·JavaScript·폰트 등 실행에 필요한 자원은 배포물에 포함한다.

## 4. AirWave 연동과 아직 남은 확인

공식 API의 기본 경로는 POST /LOGIN으로 세션 쿠키와 X-BISCOTTI 토큰을 받은 뒤 GET /ap_list.xml을 조회하는 방식이다.[S1]

현재 대화에서 실행한 진단은 인증서 검증 단계까지이며, 실제 로그인과 AP 목록 수신 성공은 확인되지 않았다. 인증서 이름, 신뢰 체인, 유효기간 관련 문제가 관측되었다. 주소·인증서·실행 계정 조건을 정리하고 실제 API 응답으로 어댑터를 검증해야 한다.

### 수집 원칙

1. 먼저 AP 목록을 일괄 조회한다. AP 2,000대에 개별 상세 조회를 반복하는 방식을 기본으로 삼지 않는다.
2. 세션 쿠키와 토큰은 실행 중 재사용하고, 프로그램을 재시작하면 다시 로그인한다.
3. HTTPS 인증서 검증을 유지한다. 전체 인증서 검증을 끄는 옵션은 v0.1 설계에 포함하지 않는다.
4. 자격 증명을 담은 요청을 다른 출처로 자동 리다이렉트하지 않는다.
5. 로그인 응답의 토큰·쿠키와 AP 목록 XML의 구조를 확인한다. HTTP 200만으로 성공으로 판단하지 않는다.
6. 서버 주소와 조회 범위를 포함한 수집 프로필의 식별자를 저장한다. 실행 시작 시 설정 버전을 고정하고, 진행 중 설정 변경은 해당 실행의 종료·반영 후 적용한다.
7. 폴더·그룹 필터가 필요하면 실제 API에서 동작을 확인한 필터만 사용한다.
8. AP 범위는 device_category 등 실제 응답의 분류를 확인하여 정한다. 컨트롤러·스위치를 AP로 합산하지 않는다.

### 스위치·전력·LLDP의 확인 범위

| 정보 | 공식 8.2.14.0 문서에서 확인한 범위 | 구현 전 확인할 범위 |
| --- | --- | --- |
| AP 기본정보·연결 장비 | AP 목록 예시에 유선 MAC·시리얼·모델·버전·컨트롤러 ID와 upstream 장비 ID·포트 인덱스가 존재. upstream 예시 값은 비어 있음 [S1] | 실제 값, 스위치 관리 IP·이름 조회, 포트 인덱스와 실제 포트명의 대응 |
| AP 전원·소비전력 | AP 모니터링 화면에 전원 유형과 소비전력 항목 [S7] | 해당 AP 모델·버전에서의 실제 값, 단위, 원천 시각, 공식 API의 필드 |
| 스위치 포트·PoE | 인터페이스 운영 상태 및 ArubaOS-Switch용 PoE 탭에 할당·실제 전력, 공급 상태·통계 등의 설명 [S8] | 모델별 화면 차이, 실제 API 필드, 포트와 AP의 정확한 연결. 모든 CX 모델에 같은 PoE 탭을 가정하지 않음 |
| 유선 이웃 | 이웃 표에 로컬·상대 포트, 발견 출처와 마지막 확인 관련 항목. LLDP/CDP 외 다른 탐색 근거도 있음 [S8] | 실제 LLDP 출처 표시, 원천의 마지막 수신·갱신 시각, 조회 범위의 완전성, TTL·수신 카운터 제공 여부 |
| 토폴로지 | 폴더 범위의 공식 토폴로지 조회 경로가 존재 [S1] | 실제 링크 데이터 구조, LLDP 근거, 규모별 응답 비용. 목록상의 노드만으로 LLDP 상태를 만들지 않음 |

- 화면에 표시되는 항목이 모두 AP 목록 API에 포함된다고 가정하지 않는다. 공식 문서에서 확인하지 못한 필드를 API에 존재하지 않는다고 단정하지도 않는다.
- AP 상세 예제의 radio 아래 neighbor_ap는 무선 RF 이웃이다. 유선 LLDP 이웃으로 매핑하지 않는다.[S1]
- PoE의 LLDP 협상 지원 여부와 실제 LLDP 이웃의 최신 관측 여부는 별개다.[S8]
- 어댑터는 프로필·장비 유형·필드별 제공 상태를 미검증 / 제공 확인 / 미지원 확인으로 관리한다. 값 누락 한 번으로 미지원으로 바꾸지 않는다. 권한·조회 실패는 실행 품질로 별도 기록한다.
- 부가 정보는 AirWave의 읽기 기능을 통해 확보한다. 수집 PC의 직접 스위치 SSH/SNMP 접속이나 비공식 웹 요청을 기본 전제로 추가하지 않는다. 공식 API로 확보하지 못한 값은 미확인으로 남기고, 대장 정보만 출처를 표시해 수동 등록할 수 있다.
- 수동 입력값은 실제 PoE 측정값이나 LLDP 정상 관측의 근거로 사용하지 않는다.

### 수집 단위와 실행 우선순위

- AP 상태·목록, 스위치 연결·이웃, PoE 측정은 각각 독립적인 수집 단위와 실행 ID·범위 버전·완전성·마지막 성공 시각을 가진다. 한 예약 주기의 전체 요약과 각 단위의 성공 여부를 구분한다.
- AP 목록에서 함께 얻는 기본정보는 같은 응답으로 처리한다. 부가 정보는 별도 주기·예산으로 조회하고 AP 상태 수집을 우선한다.
- 스위치별 중복 조회를 제거하고 검증된 범위 제한을 사용한다. 2,000개 AP마다 상세·토폴로지를 반복 호출하지 않는다.
- 동시에 한 네트워크 수집 단위만 실행한다. 부가 요청 중 AP 수집 시각이 도래하면 다음 부가 요청을 시작하지 않고 AP 실행 대기 표시 하나만 유지한다. 현재 요청 종료 또는 제한 시간 도달 후 부가 단위의 확보 결과를 부분 수집·양보 사유로 확정하고 AP 수집을 즉시 시작한다. 여러 도래 시각은 하나로 합치며 부가 수집이 끝날 때까지 AP 주기 전체를 건너뛰지 않는다.
- AP 상태 수집 자체가 아직 실행 중일 때 다음 AP 주기가 도래하면 중첩하거나 과거 실행을 쌓지 않고 건너뛴 횟수를 기록한다. 미완료 부가 작업은 다음 부가 주기로 미루며 무한 대기열을 만들지 않는다.
- 아래 요청·전체 실행 시간 한도는 각 수집 단위에 적용한다. 부가 수집을 위해 AP 상태 단위의 제한 시간을 늘리지 않는다.
- 전체 토폴로지 조회는 규모에 따라 오래 걸릴 수 있다는 공식 설명이 있다.[S1] v0.1 기본 반복 작업에서는 비활성화하며, 작은 폴더 범위의 비용·완전성이 확인되고 제한 시간 내 수행되는 경우에만 활성화한다.

### 서버와 조회 범위의 변경

- 서버 주소는 HTTPS 출처(스킴·호스트·포트)로 정규화하며 경로·사용자 정보·쿼리·프래그먼트는 허용하지 않는다.
- 서버의 출처가 바뀌면 기본적으로 새로운 AirWave 인스턴스 데이터셋을 만든다. 기존 사건은 기존 데이터셋에 보존하고 추적 종료 사유를 남긴다.
- 동일 서버의 IP를 FQDN으로 바꾸는 경우에도 v0.1은 이전 데이터셋을 자동 병합하지 않는다. 최초 실제 수집 전에 사용할 정식 주소를 확정한다.
- 자격 증명은 프로필과 서버 출처에 연결한다. 출처가 바뀌면 세션을 폐기하고 자격 증명을 다시 등록한다.
- AirWave DB 재구축·복원 등으로 AP ID의 의미가 바뀐 경우 새 데이터셋으로 시작한다. 이를 완전히 자동 감지한다고 가정하지 않는다.
- 같은 서버의 조회 범위나 로그인 계정이 바뀌면 범위 버전을 올리고 대수를 다시 확인한다. 이전 버전으로 요청한 응답을 새 범위의 누락·제외 판단에 사용하지 않는다.

### 프록시와 실행 계정

기본값은 실행 계정의 Windows 설정을 따르는 방식이다. Windows의 .NET 기본 프록시는 환경변수가 있으면 이를 먼저 사용하고, 그렇지 않으면 사용자 프록시 설정을 사용한다.[S2]

- 수동 실행 계정과 자동 수집 계정의 환경을 각각 검증한다.
- PAC URL과 고정 프록시 주소를 같은 입력값으로 취급하지 않는다.
- 진단 결과에는 선택한 연결 경로, TLS 결과, HTTP/API 결과를 구분한다.
- 인증서 신뢰 및 자격 증명 복호화도 실제 수집 계정에서 확인한다.
- 환경 설정을 자동으로 변경하거나 임의의 인증서를 신뢰 저장소에 등록하지 않는다.

### 요청과 실패 제어의 제안값

- HTTP 요청 1회의 제한 시간: 45초.
- 수집 단위 1회의 전체 제한 시간: 120초. 로그인·세션 갱신도 이 한도에 포함한다.
- 응답 크기 제한: 압축 해제 후 64 MiB. 한도를 넘으면 명시적 실패로 기록한다.
- 수집은 한 번에 하나만 실행한다. 수동 조회도 같은 실행 잠금을 사용한다.
- 동일 종류의 수집이 아직 실행 중이면 다음 같은 종류의 주기를 중첩하거나 쌓아 두지 않고 건너뛴 횟수를 기록한다. 부가 요청 중 AP 주기가 도래한 경우에는 위 AP 우선 대기 규칙을 적용한다.
- 일시적인 통신 실패는 다음 예정 주기에 재시도한다. 한 주기 안에서 반복 재시도하지 않는다.
- API의 401 또는 확인 가능한 동일 출처 로그인 화면 전환 등 세션 만료 증거가 있으면, 한 주기 안에서 재로그인과 재조회를 최대 한 번만 시도한다.
- API의 403은 권한·토큰 문제로 분류하고 무조건 재로그인하지 않는다.
- 로그인 거절 또는 세션 재인증 실패가 확인되면 자동 로그인 시도를 멈추고 자격 증명 확인이나 사용자의 명시적 재시도를 기다린다.
- TLS·네트워크·인증·권한·응답 형식·데이터·저장 실패를 서로 다른 오류 범주로 기록한다.

## 5. 데이터의 상태와 최신성

AP가 마지막으로 보고한 상태와 프로그램이 그 상태를 확인한 품질을 분리한다. 이 절의 AP 실패·누락 규칙은 AP 상태 수집 단위에 적용한다. 연결·이웃·PoE의 실패는 해당 종류의 품질에만 반영한다.

| 구분 | 예 |
| --- | --- |
| 마지막 유효 AP 상태 | Up, Down, 아직 유효 상태 없음 |
| 관측 품질 | 이번 수집에서 확인, 수집 실패, 응답에서 누락, 상태값 불명, 일정 시간 갱신 없음 |
| 수집 실행 결과 | 성공, 일부 데이터만 유효, 실패, 재시작으로 중단됨 |
| 관리 대상 여부 | 현재 조회 대상, 조회 범위에서 제외, 식별 정보 변경으로 추적 종료 |

### 수집 실패 처리

- 마지막으로 유효하게 받은 AP 상태와 그 시각을 보존한다.
- 전체 조회가 실패하면 현재 Up/Down을 새로 확인한 것처럼 집계하지 않는다.
- 화면은 최신 확인이 불가능함을 먼저 보여 주고, 필요하면 마지막 성공 시점의 대수를 별도 표기한다.
- 기존 진행 중 장애를 자동 종료하거나 새 장애를 만들지 않는다.
- 기본 주기의 2배 이상 유효 관측이 없으면 갱신 지연 표시를 추가한다. 이는 통신 장애 확정 조건이 아니다.

### 목록 누락과 불완전 응답

- 비정상 XML, 잘못된 루트, 로그인 HTML, 응답 크기 초과는 전체 수집 실패다.
- 문서 구조는 정상이지만 일부 AP의 ID·상태값이 잘못됐으면 해당 레코드는 상태 판정에서 제외하고 실행 결과를 부분 유효로 기록한다.
- 중복 AP ID는 어느 레코드가 맞는지 임의로 선택하지 않는다. 충돌한 ID 전체를 이번 판정에서 제외한다.
- 부분 유효 응답에서도 식별과 상태가 검증된 AP는 관측을 반영할 수 있다. 전체 수집 정상으로 표시하지 않는다.
- 누락·불명 상태·중복 ID로 제외된 AP는 각각 관측 공백으로 기록한다. 다른 AP의 수집이 성공해도 해당 AP의 공백을 닫지 않는다.
- 부분 유효 실행은 검증된 AP의 최종 관측 시각만 갱신한다. 전체 수집 성공 시각은 모든 기대 대상에 유효한 관측이 있을 때만 갱신한다.
- 누락된 AP는 Down이나 삭제로 단정하지 않는다. 마지막 상태와 마지막 관측 시각을 유지하면서 확인 대상으로 표시한다.
- 최초 조회가 0대이거나 기존 대상이 있는데 0대가 반환되면 대상·권한·응답 확인이 필요한 결과로 표시한다.
- 조회 범위가 바뀌면 범위 변경 이력을 남긴다. 이전 범위에서 빠진 AP의 사건을 복구된 것으로 처리하지 않는다.
- 현재 범위에서 이전에 확인한 추적 대상은 기대 대상 목록에 유지한다. 누락 대상의 추적 종료는 운영자가 사유를 남겨 명시적으로 확인하며, 사건과 과거 기록은 보존한다.
- 조회 범위 버전이 바뀌면 새 범위의 기준 목록을 별도로 수립하고 이전 범위의 제외 상태를 구분한다. 범위 변경 자체가 AP 장애·복구 사건을 만들지 않는다.

### 시각의 의미

- 프로그램이 응답을 관측한 시각과 AirWave last_contacted 값을 따로 저장한다.
- last_contacted는 AirWave 원천 정보이며 장애 시작·복구 시각으로 대체하지 않는다.
- Down인 AP의 last_contacted가 오래됐다는 사실만으로 프로그램의 수집 실패를 선언하지 않는다.
- 시각은 UTC로 저장하고 화면은 한국 표준시로 표시한다.
- 순서는 수집 실행의 증가하는 식별자로 보존한다. PC 시계 역행으로 시각이 뒤집히면 음수 장애 시간을 표시하지 않고 시간 확인 필요로 남긴다.
- AirWave의 원천 갱신 주기와 프로그램 수집 주기에 따른 감지 지연이 있다. 관측 사이에 발생했다가 복구된 짧은 장애를 모두 기록한다고 보장하지 않는다.
- 상태·연결·이웃·전력마다 수집기가 읽은 시각과 원천이 제공한 갱신·마지막 확인 시각을 따로 보존한다. API를 다시 읽었다는 이유로 오래된 원천 시각을 현재로 덮어쓰지 않는다.
- 원천 시각이 제공되지 않으면 원천 최신성 미상으로 표시한다. AP last_contacted를 LLDP 마지막 수신 시각이나 PoE 측정 시각으로 대입하지 않는다.

### 수집 회차별 Down 현황

각 AP 상태 수집 회차는 고정된 인스턴스·범위 버전과 관측 기준 시각을 가진다. 수집 요약과 AP 목록을 같은 최종 트랜잭션으로 저장하여 서로 다른 회차의 대수와 목록을 섞지 않는다.

| 구분 | 정의 |
| --- | --- |
| 이번 Down 확인 | 이번 회차에 유효한 Down을 받은 감시 대상 AP |
| 신규 Down | 이전 유효 Up에서 이번 Down으로 전환한 AP. 사이에 공백이 있으면 함께 표시 |
| 기존 미복구 Down | 열린 사건이 있는 AP에서 다시 Down을 관측. 공백 중 계속 Down이었다는 뜻은 아님 |
| 최초 확인 Down | 현재 감시 구간에서 기준 상태가 없는 장비 세대를 처음 Down으로 확인. 신규 전환과 구분 |
| 이번 복구 확인 | 동일 장비 세대의 열린 사건에서 처음 유효 Up을 확인. 교체·제외·목록 누락은 포함하지 않음 |
| 이번 확인 불가 | 기대 대상이지만 이번에 유효한 상태를 확인하지 못한 AP |
| 마지막 Down·이번 미확인 | 확인 불가 대상 중 마지막 유효 상태가 Down인 AP. 미복구 추적에서 사라지지 않게 별도 표시 |

- 이번 유효 Down은 신규 Down + 기존 미복구 Down + 최초 확인 Down으로 나눈다. 복구 건수는 이번 Up의 일부이고 별도 변화 지표이므로 전체 대수에 다시 합산하지 않는다.
- 신규·복구는 AP별로 직전에 저장한 유효 상태와 이번 실행에서 확정한 사건 전환으로 집계한다. 직전 전체 성공 회차를 비교 기준으로 삼아 부분 성공에서 이미 기록한 전환을 다시 집계하지 않는다.
- 각 회차의 신규·최초 Down·복구 확인·추적 종료 결과는 해당 AP 장비 세대와 사건 ID를 연결해 보존한다. 이후 상세 로그 만료·시계 보정·현재 상태 변경이 있어도 이 결과를 시각 비교나 대수 차이로 다시 계산하지 않는다.
- 기준 목록이 수립된 같은 범위에서 감시 대상 수 = 이번 유효 Up + 이번 유효 Down + 이번 확인 불가를 만족해야 한다. 수동 감시 제외·범위 변경은 별도 건수·사유로 보존한다.
- 최초 수집에서 전체 대상 규모를 아직 검증하지 못했으면 기준 목록 수립 중으로 표시한다. 받아온 AP 수만으로 권한·필터의 누락이 없다고 보장하지 않는다.
- 부분 성공이면 확인한 범위의 대수만 표시하고 확인 불가 수를 나란히 보여 준다. 전체 조회 실패 화면의 현재 Down은 확인 불가로 표시하며, 직전 회차의 Down은 원래 시각이 붙은 참고값으로 유지한다. 실패 회차의 유효 레코드 수 0을 Down 0대 또는 전체 정상으로 표현하지 않는다.
- Down 대수 감소만으로 복구 수를 계산하지 않는다. AP별 유효 상태 전환으로 복구를 세고, 누락·감시 제외·교체·범위 변경으로 달라진 대수는 별도로 설명한다.
- 기간별 반복 횟수는 해당 기간에 관측한 Up → Down 전환 수다. 최초 Down을 전환 횟수에 포함하지 않으며 고정된 과거 범위의 사건도 조회할 수 있다.
- 기간별 장애 사건 건수와 고유 AP 대수는 따로 표시한다. 동일 AP의 세 번 전환은 3건·1대이며 반복 지표를 현재 Down 대수에 더하지 않는다.
- 장기 미복구는 감지 후 경과시간으로 정렬·필터한다. 1시간 이상·24시간 이상 등은 조회 프리셋 제안이며 실제 연속 서비스 중단시간 또는 자동 원인 판정이 아니다. 공백과 최초 시작 미상 표시를 유지한다.

### 수집 화면의 건강 상태

- 수집기 응답 여부, 마지막 시도, 마지막 AP 상태의 유효 DB 반영, 마지막 전체 대상 확인, 다음 예정 실행과 중지/대기 사유를 구분한다. 웹 화면이 열린다는 사실만으로 AP 수집을 정상으로 표시하지 않는다.
- 화면의 서버 조회가 실패하면 화면 내 연결 끊김 표시와 마지막 표시 기준 시각을 유지한다. 마지막 정상 색상과 대수가 새 관측처럼 계속 보이지 않아야 한다.
- 저장 장애로 DB에 실패 로그조차 쓸 수 없어도 응답 가능한 로컬 상태/진단에서는 저장 실패와 마지막 저장 성공 시각을 드러낸다. 실패 응답을 메모리에 무한 적재하지 않는다.
- 저장이 다시 가능해지면 다음 유효 수집부터 반영한다. 보존하지 못한 구간은 관측 공백으로 남기며 복원했다고 주장하지 않는다. 로그 순환·백업의 실패도 AP 상태 수집 실패와 별도 표시한다.

## 6. AP 식별과 장애·복구 사건

### AP 식별

- 기본 연결 키는 AirWave 인스턴스 식별자 + AirWave AP ID다.
- 이름과 IP는 바뀔 수 있는 속성이므로 장비 식별 키로 사용하지 않는다.
- 일련번호와 LAN MAC은 응답에 있을 때 보조 식별 정보로 저장한다.
- 다른 AP ID를 가진 기록을 이름·IP가 같다는 이유로 자동 병합하지 않는다.
- 동일 AP ID에서 기존에 확인된 하드웨어 식별자가 바뀌면 새 장비 세대로 분리한다. 비교 우선순위는 일련번호, 일련번호를 사용할 수 없을 때 LAN MAC이다.
- 보조 식별자가 응답에서 빠진 것만으로 교체로 판단하지 않는다.
- 장비 세대가 바뀐 경우 기존 열린 사건은 추적 종료 사유를 남기고 복구 시각을 만들지 않는다.
- 장비 세대 분리를 상태 전환보다 먼저 적용한다. 새 세대의 이전 상태는 없음이며, 교체 장비의 Up을 구장비 장애의 복구로 기록하지 않는다.
- 중복 ID로 제외한 레코드는 상태 판정뿐 아니라 식별 정보·장비 세대 변경에도 사용하지 않는다.
- 자동 감지한 식별자 변경은 장비 세대 분리와 함께 교체 확인 필요로 기록한다. 운영자의 교체 작업 기록이 없으면 물리 교체를 확인했다고 표현하지 않는다.
- AP 이름·IP를 재사용한 신규 장비는 과거 장비의 연결·이웃·전력 최신성을 물려받지 않는다. 기존 값은 구장비 사건이나 설치 지점의 과거 참고 정보에만 남긴다.

### 상태 전환 규칙

| 이전에 유효하게 관측한 상태 | 이번 유효 상태 | 처리 |
| --- | --- | --- |
| 없음 | Up | 기준 상태 등록. 복구 사건 생성 없음 |
| 없음 | Down | 최초 확인 당시 Down 사건 생성. 실제 시작 시각 미상 표시 |
| Up | Down | 새 장애 사건 1개 생성 |
| Down | Down | 같은 열린 사건의 마지막 Down 관측 갱신 |
| Down | Up | 기존 사건에 첫 복구 확인 시각 기록 |
| Up | Up | 현재 관측 갱신. 장애 사건 생성 없음 |
| 어느 상태든 | 이번 관측 불가 | AP 상태 전환·복구 없음. 관측 품질과 수집 결과만 변경 |

- 기본 정책은 한 번의 유효 관측을 반영하는 것이다. 추가로 두 번 Down을 기다리는 규칙을 고정하지 않는다.
- 현재 장비 세대마다 열린 장애 사건은 최대 하나다.
- 재시작 후 DB의 마지막 상태와 열린 사건을 복원한다.
- 수집 중단 구간을 거쳐 다시 관측한 경우 해당 사건에 관측 공백이 있었다는 표시를 남긴다.
- Up → 관측 공백 → Down은 새 사건을 만들되 마지막 Up과 첫 Down 사이에 공백이 있음을 함께 기록한다.
- Down → 관측 공백 → Down은 같은 열린 사건을 유지하지만, 공백 동안 계속 Down이었다고 단정하지 않는다.
- Down → 관측 공백 → Up은 재개 후 첫 Up 시각을 복구 확인 시각으로 기록하고 실제 복구 시각은 알 수 없음을 표시한다.
- 조회 범위를 벗어난 열린 사건은 추적 중지로 표시해 현재 감시 대상 집계에서 분리한다. 다시 대상이 되면 공백을 표시하고 관측을 이어간다.
- 위 일시 중지와 명시적 추적 종료를 구분한다. 사유를 남겨 추적 종료한 동일 장비가 재편입되면 새 감시 구간을 시작해 상태 전환의 기준을 없음으로 둔다. 물리 장비 세대와 과거 사건은 유지하되 종료 사건을 재개하거나 복구 처리하지 않는다. 첫 유효 Down은 새 구간의 최초 확인 Down이다.
- 운영자 메모는 자동 상태와 독립적인 부가 정보다. 메모 입력으로 AP를 Up 처리하거나 사건을 복구 완료로 바꾸지 않는다.

### 사건에 남길 최소 정보

- 내부 사건 ID, 내부 AP 식별자, AirWave 인스턴스/AP ID, 장비 세대.
- 당시 AP 이름·IP·유선 MAC·시리얼·모델·펌웨어·폴더·그룹·위치·컨트롤러와 관리 상태.
- 감지 당시와 복구 확인 당시 각각 확보한 스위치·포트·이웃·PoE 정보의 불변 스냅샷. 값별 원천·관측 시각·품질 포함.
- 마지막 Up 관측, 첫 Down 관측, 마지막 Down 관측, 첫 복구 확인 시각.
- 최초 관측 시 이미 Down인지, 관측 공백이 있었는지, 추적 중지·종료 사유.
- 사건 상태: 관측 중, 복구 확인, 추적 종료. 별도로 추적 일시 중지 여부.
- 운영자 메모와 메모 수정 시각.

화면의 시간 항목은 장애 감지 시각, 복구 확인 시각, 감지 후 경과시간 또는 감지~복구 확인 간격으로 표시한다. 정확한 서비스 중단 시간으로 표현하지 않는다. 반복 장애 횟수는 확인된 Up → Down 전환 횟수로 정의하고, 최초 확인 당시 Down인 건은 따로 구분한다.

### 장비·위치·연결 정보의 저장 항목

| 분류 | 저장 항목 및 의미 |
| --- | --- |
| AP 식별 | 내부 ID, AirWave 인스턴스/AP ID, 장비 세대, 이름, IP, 유선 LAN MAC, 시리얼. 무선 BSSID와 구분 |
| 장비 정보 | 모델, 펌웨어, 확보되는 재부팅·가동시간 보조 정보. 재부팅 추정만으로 장애 원인을 확정하지 않음 |
| 위치 | 사업장·건물·층·구역·상세 위치, 별도 설치 지점 ID. AirWave의 SNMP 위치 문자열·폴더·그룹 원본과 구분 |
| 논리 연결 | 컨트롤러 ID·이름·IP. 물리 연결 스위치와 별도 관계 |
| 물리 연결 | 스위치 내부/원천 ID·이름·관리 IP, 실제 포트명·원천 포트 인덱스, AP 측 인터페이스, 관측 방향 |
| 관리 상태 | 운영·작업·철거·감시 제외 등 운영자가 지정한 상태와 변경 사유. 원천 유지보수 표시와 구분 |
| 데이터 근거 | 자동/수동/가져오기 출처, 수집 실행·범위 버전, 수집기 관측 시각, 원천 시각, 유효성·완전성·최신성 |

- 설치 지점 ID는 이름·IP·자유 입력 위치 문자열로 자동 생성·병합하지 않는다. 운영자가 등록하거나 기존 대장의 고유 키를 확인해 연결한다. 장비 교체와 위치 이동은 각각 배치 관계의 시작·종료 관측 및 실제 작업 시각으로 기록한다.
- 장비별 이력과 설치 지점별 이력을 모두 조회할 수 있다. 다른 AP ID를 같은 지점에 연결하더라도 물리 장비의 사건·세대를 병합하지 않는다.
- 스위치는 AP 집계에 포함하지 않으며 이름·IP만으로 동일 장비를 단정하지 않는다. 관리되지 않는 이웃은 출처가 제공한 장비 식별자의 종류와 값을 보존한다.
- AP 하나에 연결 하나만 있다는 DB 제약을 두지 않는다. 여러 유선 인터페이스·후보가 관측되면 모두 보존하고, 대표 연결이 불명확하면 임의로 선택하지 않는다. 한쪽에서 본 이웃을 양방향 확인으로 표시하지 않는다.
- 연결 관계에는 최초 확인·마지막 확인·부재 확인 또는 추적 종료 시각과 근거를 남긴다. 새 연결 하나를 발견했다는 이유만으로 기존 연결을 닫지 않는다. 동일 인터페이스·범위의 완전한 관측 또는 명시적 작업 기록으로 종료 의미를 구분한다.
- 유효하지 않은 상태값 때문에 AP 상태 판정을 제외해도, 장비 식별이 검증된 별도 필드는 필드별 검증을 거쳐 기록할 수 있다. 중복 ID 등 식별 충돌이 있으면 그 레코드의 모든 자동 변경을 제외한다.

### 변경·교체·작업 이력

1. 장애·복구, 기본정보, 스위치·포트 연결, 장비 교체, 펌웨어·컨트롤러, 작업·조치의 여섯 종류를 시간순으로 조회한다.
2. 변경에는 대상 장비·세대/설치 지점, 항목, 이전값, 새값, 감지 시각, 원천 시각(있는 경우), 출처, 수집 실행, 확인 품질을 남긴다. 실제 작업 시각은 운영자가 별도로 입력하며 자동 감지 시각과 혼용하지 않는다.
3. 최초 확보값은 기준 정보 등록이다. 이후 같은 의미의 유효 값끼리 비교해 변경 사건을 만든다. MAC 표기·앞뒤 공백 등 검증된 정규화만 적용한다.
4. API 누락·빈 값·조회 실패·권한 변경은 이름/IP/포트 삭제나 물리 연결 해제로 바꾸지 않는다. 명시적인 수동 해제 또는 완전하고 최신인 동일 범위 관측에서 확인된 부재를 별도로 기록한다. 이웃 미관측도 케이블 분리 확정과 구분한다.
5. 공백 전후 값이 다르면 변경을 재개 후 발견한 것으로 남긴다. 공백 동안 정확히 언제, 몇 번 바뀌었는지는 추정하지 않는다.
6. 수동 등록값과 자동 관측값은 각각 보관한다. 수동 우선값과 자동값이 다르면 차이를 표시하며 조용히 덮어쓰지 않는다. 출처 선택 변경은 물리 이동 사건으로 처리하지 않는다.
7. 직접 입력·CSV 가져오기는 내부 장비/지점 키 또는 유일하게 확인된 시리얼·유선 MAC으로 대조하고 변경 미리보기를 제공한다. 이름/IP 충돌, 중복 행, 식별 불가 행은 적용하지 않고 결과를 표시한다. CSV의 Up/Down·전력·LLDP 입력은 자동 관측으로 등록하지 않는다.
8. 작업에는 작업 ID, 대상 장비·지점·사건, 작업 종류, 예정 기간(선택), 실제 작업 시각, 기록 시각, 작업자(선택), 내용, 결과, 확인된 원인/확인 중 구분, 메모를 남긴다. 같은 작업에 여러 대상 사건을 연결할 수 있다.
9. 작업·메모의 수정은 수정 시각과 이전 버전을 보존한다. 정정·취소는 자동 수집 사실을 덮어쓰지 않는다. 계획 작업 중의 Down도 관측 사실로 유지하고 작업 기간과의 관계를 표시한다.
10. 철거·감시 제외는 사유와 시각을 남겨 추적 상태를 바꾼다. 장비 삭제나 장애의 자동 복구 처리가 아니다.

### 장애 당시 정보 보존

- 장애 사건을 저장하는 시점에 DB에 반영되어 있는 마지막 유효 장비·연결·전력·이웃 값을 각자의 관측 시각·원천 시각·품질과 함께 복사한다. 예를 들어 14:05 Down에 14:00 연결 정보가 붙으면 14:00에 확인한 마지막 연결로 표시한다.
- 이번 AP 목록에 유효한 새 정보가 있다면 같은 AP 상태 트랜잭션 안에서 먼저 반영한 뒤 스냅샷을 만든다. 식별·장비 세대 검증은 그보다 먼저 한다.
- 사건 생성 뒤에 도착한 부가 응답으로 감지 당시 스냅샷을 소급 갱신하지 않는다. 후속 관측은 사건과 연결된 별도 기록이며 복구 확인 스냅샷도 별개다.
- API에서 연결 정보가 사라져도 마지막 유효 정보를 원래 시각과 함께 보존한다. 값이 없으면 미확인으로 남기며 현재 연결이나 이번에 측정한 값처럼 표시하지 않는다.

### LLDP·포트·PoE의 관측과 판정

| 표시 | 필요한 근거 |
| --- | --- |
| LLDP 이웃 관측 | 동일 장비·포트를 식별한 이웃 레코드에 LLDP 출처가 명시됨. 원천 최신성을 별도로 표시 |
| 이웃 관측·프로토콜 미확인 | 연결은 확인되지만 LLDP/CDP 등 발견 출처가 제공되지 않음 |
| 최신 원천 확인 | 해당 종류의 원천 갱신/마지막 수신 의미와 시각이 검증되고 허용 범위 안에 있음. 수집기 조회 성공만으로 부여하지 않음 |
| 원천 최신성 미상 또는 갱신 지연 | 원천 시각이 없거나 해당 종류의 갱신 기준을 넘음. 마지막 유효 값은 보존 |
| 이웃 미관측 | 해당 포트 범위가 완전하고 최신인 유효 응답에서 기존 기대 이웃이 확인되지 않음. LLDP·AP 장애 확정과 구분 |
| 수집 실패·미지원·미검증 | 각각 통신/권한 실패, 제공되지 않음이 확인됨, 아직 데이터 계약을 확인하지 못함 |

- 원천 최신성의 허용 범위는 어댑터가 실제 원천 갱신 주기·시각 의미를 확인한 뒤 설정한다. LLDP TTL은 API가 명시적으로 제공하고 의미가 확인된 경우에만 보조 근거로 사용하며 임의의 TTL 값을 만들지 않는다.
- Upstream 장비 표시, 포트 Up, PoE 공급 중, LLDP 협상 기능 사용 가능은 서로 독립된 정보다. 한 항목으로 나머지의 정상 상태를 자동 확정하지 않는다.
- 같은 이웃을 반복해서 확인한 구간은 관측 범위에서 유지로 표현한다. 관측 사이의 무중단·양방향 LLDP 송수신이나 무선 서비스 정상까지 보장하지 않는다.
- PoE는 AP 소비전력, 스위치 포트 실제 전력, 요청·할당·예약·최대 전력, 전원 유형, 공급 상태 및 제공되는 오류 카운터를 의미별로 나눈다. 값·단위·측정 지점·원천 시각을 보존하고 미제공값을 0으로 채우지 않는다.
- 포트 전력 표본은 스위치·포트에 귀속한다. AP와 연결할 때에는 해당 표본 시각에 적용할 수 있는 연결 관측의 ID·시각·품질을 함께 남긴다. 관계가 오래되거나 불명확하면 AP에 확정 귀속하지 않는다. 현재 연결 관계로 과거 표본의 AP를 재해석하지 않는다.
- W는 전력, Wh/kWh는 누적 에너지로 구분한다. RF 송신전력(dBm)을 PoE 소비전력으로 매핑하지 않는다. v0.1은 전력 측정값과 추이를 대상으로 하며 누적 에너지의 검침·정산 기능을 포함하지 않는다.
- 전력 수치 변화는 측정 이력으로 저장한다. 매번의 소수점 변화마다 AP 정보 변경 사건을 만들지 않는다. 포트·PoE 공급 상태 또는 이웃 관측 상태의 유효 전환은 별도 관측 사건으로 남기고 반복된 같은 상태는 중복 생성하지 않는다.
- 이웃·PoE·포트 상태 변화만으로 AP Up/Down을 바꾸거나 장애 원인을 확정하지 않는다. 같은 스위치의 동시 Down은 조사에 사용할 상관 정보로 표시한다.

## 7. 저장, 보존, 백업

### 논리 데이터 구성

- 상세 테이블명과 코드 인터페이스는 승인 후 구현 계획에서 정한다.
- AP 상태 수집 단위에서 검증된 AP의 현재값, 장비 세대·사건 전환·스냅샷, 회차별 Down/확인 불가 현황, 해당 단위의 공백·변경 이력·최종 결과·건수·성공 시각을 하나의 DB 트랜잭션으로 저장한다.
- 연결·이웃·PoE 단위는 각각 자신의 현재값·표본·변경 사건·품질·공백·실행 결과를 별도 트랜잭션으로 저장한다. 네트워크 응답을 기다리는 동안 DB 쓰기 트랜잭션을 유지하지 않는다.
- AP 상태 성공 후 이웃 조회가 실패해도 앞서 확정한 AP 상태·사건을 롤백하거나 미확인·Down으로 바꾸지 않는다. 예약 주기의 요약은 각 단위의 결과로 계산한다. 미지원·비활성 기능은 반복 수집 실패로 집계하지 않는다.
- 실행 시작 기록은 별도로 먼저 저장할 수 있다. 최종 반영에는 데이터 종류와 실행 ID별 중복 방지 제약을 두어 같은 실행을 두 번 적용하지 않는다.
- 저장 시 수집 시작 당시 고정한 프로필·범위와 대상 식별/장비 세대를 대조한다. 서로 다른 데이터셋·범위·세대의 결과를 결합하지 않는다.
- 저장 실패 시 부분 반영을 롤백하고 마지막 성공 시각을 갱신하지 않는다.
- 프로세스 중복 실행 방지와 DB 제약으로 중복 사건을 방지한다.
- SQLite는 로컬 디스크에 두고 WAL 모드를 사용한다. 쓰기는 백그라운드 프로세스에서 직렬화한다.[S3]
- DB·설정·비밀 저장 파일·로그는 실행 파일 교체 위치와 분리한 영구 데이터 디렉터리에 둔다.
- 기본 데이터 위치는 %ProgramData%\AirWaveAPMonitor로 제안하며 실제 실행 계정에 필요한 접근 권한을 부여한다.

2,000대를 5분마다 모두 누적하면 하루 576,000행, 30일에 17,280,000행이 된다. 이는 2,000 × 288 × 30의 계산이며 용량 실측 결과가 아니다. AP 상태·기본정보는 현재값과 변경 사건을 저장하고, 회차별 현황은 요약과 Down/확인 불가 대상에 필요한 정보만 보관한다. 동일한 목록·표시 정보는 불변 버전을 참조해 재사용할 수 있지만 회차별 시각·품질·분류를 생략하지 않는다. 전체 AP가 Down 또는 미확인인 경우의 용량도 측정하며 임의로 대상을 잘라 저장하지 않는다. 별도 전력 표본은 활성화된 대상·주기·보존 기간을 기준으로 용량을 측정하며, 동일 표본의 중복 재수신은 원천 식별/시각이 검증되는 경우에만 제거한다.

### 보존과 백업 정책 제안

- 장애 사건·당시 스냅샷, 변경·연결·교체·이웃/PoE 상태 전환 이력, 작업·메모와 수정 기록: 자동 삭제 없음.
- 회차별 Down 현황 요약·Down/확인 불가 목록과 해당 당시 표시 정보: 자동 삭제 없음. 수집 실행의 상세 로그가 만료되어도 회차의 범위·시각·결과·품질·집계와 목록 조회를 유지한다.
- 전력의 주기별 수치 표본: 기본 30일 보존 제안. 삭제 후에도 사건 스냅샷과 상태 전환은 유지. 원시 수치의 영구 보존이나 누적 에너지 산출을 약속하지 않는다.
- 수집 실행 및 관측 공백 상세 기록: 90일. 사건에 남은 공백 표시는 상세 기록이 만료돼도 유지.
- 기준 대상 목록·범위 버전, 현재 상태와 열린 사건이 참조하는 정보, 미종결 공백은 상세 기록 정리로 삭제하지 않는다. 과거 회차 현황 조회에 필요한 불변 참조도 보존한다.
- 운영 로그: 30일, 파일 크기 제한과 순환 보관.
- 원문 API 응답: 기본 저장 안 함.
- DB 온라인 백업 API를 이용해 하루 한 번 백업하고 성공 검증된 최근 7개를 보관한다.[S4]
- 업데이트 전에는 별도 백업을 만든다. 실패한 새 백업 때문에 기존 정상 백업을 먼저 지우지 않는다.
- 복원은 수집기를 정지한 상태에서 스키마와 DB 무결성을 확인한 뒤 수행한다.
- 복원 후에는 재개 시점까지의 관측 공백을 표시한다.
- 같은 PC의 백업은 프로그램 업데이트·DB 복원용이며 PC 저장장치 자체의 손실까지 보장하지 않는다.

## 8. 화면에서 할 수 있어야 하는 작업

구체적인 배치와 시각 디자인은 별도 화면 검토로 정한다. 다음은 화면 기능 요구사항이다.

1. 첫 화면은 Down 현황이다. 관측 기준 시각·수집 상태, 이번 유효 Down·신규 Down·복구 확인·확인 불가를 표시한다. 열린 미복구 사건은 이번 Down 확인과 마지막 Down이나 이번 미확인으로 나눠 볼 수 있어야 한다.
2. AP 목록: 이름/IP/MAC/시리얼/위치/폴더/그룹/컨트롤러/스위치/포트/상태/최종 관측으로 검색·정렬·페이지 조회. 모든 세부 항목을 기본 목록의 열로 강제하지 않는다.
3. AP 상세: 현재 정보, 장애·복구, 기본정보·연결·교체·펌웨어·컨트롤러 변경, 작업·조치의 시간순 이력. 장비 기준과 설치 지점 기준 조회를 구분한다.
4. 사건 목록: 진행 중/복구 확인/추적 종료, 기간, AP·위치·스위치 조건으로 조회. 같은 스위치·시간대의 사건을 함께 볼 수 있지만 공통 원인을 자동 확정하지 않는다.
5. 수집 기록: AP 상태·연결·이웃·PoE별 마지막 성공, 원천 최신성, 오류 범주, 다음 실행 예정, 조회 건수와 소요 시간.
6. 설정·진단: 서버 주소, 자격 증명 등록, 수집 주기, 조회 범위, 연결 진단.
7. CSV 내보내기: 화면의 필터 조건과 관측 시각을 포함. 한글 Excel 사용을 고려한 UTF-8 BOM 및 수식으로 해석될 수 있는 값 처리.
8. 누락 대상 확인: 실제 관리 대상에서 빠진 AP의 추적 종료와 사유 기록. 과거 이력을 삭제하거나 복구로 바꾸지 않는다.
9. 연결·전원 상세: 스위치·포트·이웃 출처·마지막 확인·최신성, 포트 상태, 의미별 전력값·단위와 보존 기간 내 추이. 미확인·미지원·수집 실패를 0 W 또는 정상으로 표시하지 않는다.
10. 운영 기록: 작업 예정/실시, 조치 내용·결과·메모, AP 교체와 설치 지점 연결, 직접 입력·CSV 가져오기 미리보기 및 충돌 확인.
11. 회차별 현황: 특정 수집 회차와 기간의 Down 대수·해당 AP·당시 표시 정보·신규/복구 변화를 조회한다. 현재 이름·IP·SW·포트 변경으로 과거 회차의 표시 정보가 바뀌지 않는다.

Down 목록의 기본 항목은 AP 이름·IP, 설치 위치, 확보한 SW 이름/IP/포트, 첫 Down 감지, 감지 후 경과, 마지막 Down 확인, 이번 확인 여부와 작업/제외 표시다. 최근 감지순과 오래된 미복구순 정렬을 제공한다. 계획 작업 Down은 기본 현황에 포함하고 구분 태그·필터를 제공하며, 사용자가 제외 필터를 적용하면 숨긴 대수를 표시한다.

화면의 검색·조회 필터는 표시 대상만 바꾸며 실제 수집 범위를 바꾸지 않는다. 감시 범위 변경은 설정에서 명시적으로 수행하고 범위 버전과 변경 이력을 남긴다.

수집 중지와 브라우저 닫기는 서로 다른 동작이다. 수집이 중지되어도 기존 이력은 조회할 수 있어야 한다.

## 9. 실행·인증정보·로컬 접근

### 자동 실행

- Windows 서비스로 백그라운드 EXE를 운영하는 방식을 우선 제안한다.[S5]
- 동일 실행 파일의 대화형 실행도 진단과 초기 확인을 위해 제공한다.
- 서비스 설치를 사용할 수 없으면 동일 수집기의 작업 스케줄러 실행을 배포 대안으로 검토한다.
- 실제 채택할 자동 실행 방식과 실행 계정은 사내 PC의 권한·정책 확인 후 배포 전에 결정한다.
- 서비스나 예약 작업 설정은 설치 절차에서 명시적으로 수행한다. 앱 첫 실행이 임의로 시스템 설정을 변경하지 않는다.
- 실제 운영 완료 기준에는 선택한 방식으로 재부팅 후 수집이 재개되는지 확인하는 항목을 포함한다.
- 예약 작업을 선택하면 실행 제한 시간, 중복 실행, 로그온 여부와 네트워크 자격 증명 조건을 확인한다.
- 시작·재부팅·절전 복귀 후에는 허용된 연결 상태에서 AP 상태 수집 1회를 우선 수행하고 정상 주기로 복귀한다. 놓친 주기를 몰아서 실행하지 않는다. 인증 거절로 자동 로그인 중단 상태인 경우에는 그 중단을 유지한다.
- 설치 방식에 맞는 비정상 종료 후 재시작 정책을 확인한다. 사내 PC의 실제 절전 조건도 상시 운영 전 확인하며 임의로 전원 정책을 변경하지 않는다. 중단된 시간에는 정상 관측을 만들어 채우지 않는다.

### 자격 증명

- AirWave 자격 증명은 설정·진단 화면에서 입력하고, 실제 수집기 실행 계정 범위의 Windows DPAPI로 보호하여 저장한다.[S6]
- 브라우저는 보호된 파일을 직접 읽지 않으며, 백그라운드 프로세스가 등록과 복호화를 담당한다.
- 실행 계정이 바뀌거나 복호화가 실패하면 자격 증명을 다시 등록해야 한다.
- 쿠키와 X-BISCOTTI 토큰은 메모리에 보관하고 일반 로그·CSV·백업 문서에 출력하지 않는다.
- DB 백업을 다른 PC에 복원하면 자격 증명을 다시 등록한다.

### 로컬 웹 접근

- 이 초안은 운영자 한 명이 신뢰하는 Windows 사용자 환경에서 사용하는 것을 전제로 한다. 같은 PC의 서로 신뢰하지 않는 계정을 격리하는 앱 로그인·권한 모델은 포함하지 않는다.
- 루프백은 네트워크 접근 범위 제한이며 사용자 인증을 대체하지 않는다. 공용 PC의 계정별 격리가 필요해지면 구현 전에 접근 모델을 다시 정한다.
- 루프백에만 바인딩하고 허용된 Host와 동일 출처 요청을 확인한다.
- 변경 요청에는 위조 요청 방지 토큰을 적용하고 GET 요청으로 설정·상태를 변경하지 않는다.
- CORS를 외부 출처에 개방하지 않는다.
- 일반 사용자 비밀이나 내부 데이터가 외부 리소스 요청으로 전송되지 않도록 모든 UI 자원을 로컬에서 제공한다.
- 실제 주소, 계정, 인증서, AP 목록, DB, 실행 로그는 GitHub에 저장하지 않는다. 공개 저장소에는 가상 예제 데이터만 둔다.

## 10. 단계별 개발 및 검증 순서

| 단계 | 산출물 | 통과 기준 |
| --- | --- | --- |
| 0. 설계 검토 | 이 설계 문서와 검토 기록 | 요구 범위와 제안값을 검토하고 구현 기준 확정 |
| 1. 연결 어댑터 | 진단, 로그인, AP 목록 파싱, 필드별 제공 기능표 | 샘플 검증과 실제 수집 계정의 API 확인을 구분하여 기록 |
| 2. 핵심 이력 저장 | 현재 상태, 장애·복구 사건·스냅샷, 회차별 Down/확인 불가 현황 | 상태 전환·실패·누락·공백·재시작 및 회차별 집계·목록 일치 |
| 3. Down 현황 조회 | Down 우선 화면, 신규·미복구·복구·반복 조회, 필터·CSV | 장비·위치·스위치·기간·회차별 조회와 미확인 상태 구분 가능 |
| 4. 상시 운영 | 자동 시작, 백업, 로그, 배포물 | 선택한 운영 방식에서 재부팅 후 수집 재개 및 이력 유지 |
| 5. 운영 확인 | 실제 AirWave 비교 결과 | 조회 범위·대수·상태·장애 이력이 실제 환경과 일치하는지 사용자 확인 |

승인된 기본정보·연결·교체·펌웨어·컨트롤러·작업 이력과 해당 화면은 공통 저장 기반 위에서 병행·후속 구현한다. 스위치·포트·이웃·PoE 어댑터는 제공 정보·단위·시각·완전성·비용을 확인한 항목부터 활성화한다. 이 부가 검증은 위 핵심 감시 경로의 필수 선행 단계가 아니며, 핵심 감시가 동작해도 전체 승인 범위의 완료 여부는 따로 표시한다.

실환경 API 연결이 미해결이어도 가상 응답을 이용한 파싱·상태 처리·저장·화면 개발은 가능하다. 실환경 확인 항목은 별도 상태로 남기며 완료로 계산하지 않는다.

### 실환경에서 확인할 전제

- 연결 확인 전: 정식 HTTPS 주소, 인증서 이름·신뢰·유효기간, 실제 계정의 API 인증 방식과 조회 범위.
- 부가 수집 활성화 전: 대표 AP와 해당 스위치에서 연결 ID·실제 포트명·PoE 의미/단위·LLDP 출처/원천 시각의 데이터 계약, 모델별 제공 차이, 조회 완전성·소요 시간. 실제 사내 자료를 저장소에 업로드할 필요는 없다.
- 배포 전: Windows 버전·CPU 아키텍처, 자동 시작 방식의 허용 여부, 실행 계정과 데이터 폴더 접근 권한.
- 운영 확인 전: 동일 실행 계정에서의 프록시·인증서·자격 증명 복호화, 재부팅 후 재개, 실제 AirWave와 대수·상태 비교.
- 최초 운영과 조회 범위 변경 시: 같은 AirWave 계정·필터로 조회한 대상 AP 대수·기준 목록 대조. 권한 변경이나 일부 누락 때문에 기대 대상을 조용히 축소하지 않는지 확인.
- 이 항목은 실환경 완료 기준이다. 아직 확인하지 않은 값을 확인 완료로 가정하거나 제품 검증 완료율에 포함하지 않는다.

### 의미 있는 검증 시나리오

- Up → Down → Down → Up: 장애 1건과 복구 1회.
- 처음 확인할 때 Down: 실제 시작 시각 미상, 복구 시 첫 Up 관측 기록.
- Up → 수집 실패: 새 Down 사건 없음, 현재 상태를 새로 확인했다고 표시하지 않음.
- Down → 수집 실패 → 재시작 → Down → Up: 중복 사건 없음, 관측 공백 표시.
- 정상 XML 일부 누락·불명 상태·중복 ID·0건: 대량 장애/삭제 오판 없음.
- 로그인 HTML을 반환하는 HTTP 200: AP 목록 성공으로 판정하지 않음.
- 세션 만료와 잘못된 비밀번호: 제한된 재인증과 반복 로그인 중단.
- 수집과 DB 저장 도중 프로세스 종료: 재시작 후 부분 사건이나 중복 사건 없음.
- AP 이름/IP 변경, 하드웨어 식별자 변경, 조회 범위 변경: 이력 대상과 추적 상태 유지.
- 동일 이름/IP의 AP 교체 또는 같은 지점의 AP ID 변경: 장비 이력 분리, 지점 이력 연결, 구장비의 허위 복구 없음.
- 현재 스위치·포트 변경 또는 늦게 도착한 부가 정보: 이전 장애 스냅샷과 표본 귀속 불변.
- 다중 연결·일부 이웃 누락·빈 포트 값: 임의 단일화·연결 해제 없음. 완전하고 최신인 조회의 부재만 별도 기록.
- LLDP 출처 불명·원천 시각 미제공·오래된 응답 재조회: LLDP 정상 유지나 원천 최신성으로 오표시하지 않음.
- AP 상태 성공 후 PoE/이웃 실패 또는 재시작: AP 상태 확정 유지, 데이터 종류별 품질·공백과 중복 반영 방지.
- 부가 요청 진행 중 AP 수집 시각 도래: 현재 요청 종료 후 AP 실행 1회, 다음 부가 요청 진행 없음. AP 자체가 장기 실행 중이면 중첩·대기열 없이 다음 주기 건너뜀 기록.
- 전력 누락·단위 차이·할당값과 실측값·장비 교체: 0 W 대체, RF 전력 혼용, 과거 AP 귀속 변경 없음.
- 수동 정보와 자동 관측 충돌·CSV 식별 충돌: 조용한 덮어쓰기·오장비 적용 없음. 직접 입력한 LLDP/전력은 관측으로 취급하지 않음.
- 계획 작업·메모 정정·감시 제외: 자동 장애·복구 사실 유지, 작업과 수정 이력 보존.
- PC 시각 역행: 음수 시간이나 잘못된 관측 순서 표시 없음.
- 2,000대 및 5,000대 가상 목록: 정확한 파싱·집계, 수집 중첩 없음, 자원 사용량 측정.
- 선택한 운영 계정에서 프록시/TLS/API 확인, 브라우저 종료와 재부팅 후 수집 유지.
- DB 백업·복원과 실행 파일 교체 후 이력 유지.
- 저장 공간 부족·읽기 전용 DB: 저장 실패 표시, 성공으로 위장하지 않음.
- 부분 성공·전체 실패·범위 변경: 회차별 대수와 목록 일치, 실패를 Down 0대 또는 복구로 표시하지 않음.
- 수집 실행 상세 90일 경과, 이후 AP 이름·IP·연결 변경: 보존한 과거 회차의 Down 목록·분류·품질 조회 유지.
- 창만 열린 상태에서 수집 중지·서버 응답 중단·DB 기록 실패: 정상 감시로 표시하지 않음.
- 재부팅·절전 복귀·비정상 종료: AP 수집 1회 우선 재개, 누적 실행 폭주 없음, 기존 사건 중복 생성 없음.
- 일시 중지 후 재편입과 명시적 추적 종료 후 재편입: 전자는 공백을 둔 기존 사건 유지, 후자는 새 감시 구간의 최초 상태 등록. 종료된 사건의 허위 복구·재개 없음.

## 12. 검토 상태

- 요구사항 확인: 로컬 전용, 자동 수집, Up/Down 중심. 사용자의 전체 반영 요청에 따라 여섯 종류 운영 이력과 저장 항목 확대를 반영.
- 목표 재확인: 주기적 Down 현황 추적을 첫 화면·회차별 저장·개발 순서의 기준으로 명시. 승인된 보조 이력은 유지하며 핵심 감시의 완료 상태와 분리.
- 기술·기본값: 이번 초안의 설계자 제안이며 사용자 최종 검토 대상.
- 독립 설계 검토: 구현 계획 작성 관점의 검토와 상태·이력 일관성 검토를 수행했다.
- 반영한 보완: 데이터 종류별 원자적 저장·실패 분리, AP별 관측 공백, 설정 버전 고정, 장비 세대 우선 처리, 서버 출처와 자격 증명의 연결, 로컬 접근의 신뢰 범위, 설치 지점과 복수 연결, 불변 사건 스냅샷, 수동/자동 정보의 분리.
- 남은 데이터 확인: 실제 PoE·LLDP API 필드와 원천 시각, 모델별 제공 범위, 포트 매핑, 조회 비용·완전성. 제공이 검증되기 전에는 자동 수집이나 LLDP 정상 유지 판정을 완료로 표시하지 않는다.
- 제품 구현: 아직 시작하지 않음.
- 실환경 API 성공: 아직 확인되지 않음.
- 다음 산출물: 설계 검토 후 작업 단위와 검증 기준을 담은 세부 구현 계획.
